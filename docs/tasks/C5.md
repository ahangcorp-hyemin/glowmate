# C5 — 엔티티 해소 (동일 업체 병합)

> 계약 규격: [02-task-contract-spec.md](../02-task-contract-spec.md) §1 (R-6·R-7 반영)
> **v2 (2026-08-03)** — 감사 REVISE 반영: 전이 병합 봉쇄(클러스터 불변식) · 블로킹 재현율 · F2 정합화 · 홀드아웃 분리
> 상태: 착수 대기 (⛔ G1·G3 통과 + 아래 **선행 조건** 충족 후)

---

## 설계 전제 — 비대칭 판단 (유지)

**과잉병합(서로 다른 업체를 하나로 합침)이 과소병합(같은 업체가 중복 노출)보다 치명적이다.**

| | 과잉병합 | 과소병합 |
|---|---|---|
| 데이터 진실성 | A업체 상세에 B업체 가격·전화번호가 표시됨 → **거짓 정보** | 정보는 전부 참, 중복일 뿐 |
| 사용자 피해 | 잘못된 가격을 믿고 전화·방문 | 목록이 지저분함 |
| 업체 피해 | 타 업체 정보 혼입 → 정정 요구·분쟁. **업체 미접촉 방침이라 발견 경로가 W7 신고뿐** | 없음 |
| 회복 | 링크 이력이 없으면 복원 불가, 재크롤 필요 | 나중에 병합하면 즉시 회복 |

→ **정밀도 우선.** 회색지대는 병합하지 않고 검수 큐로 보낸다. 이 비대칭이 REQ-1(precision 0.99) vs REQ-2(recall 0.85),
그리고 FORBID 6개 중 5개가 과잉병합 전용이라는 구성에 반영되어 있다.

**v2 추가 — 쌍(pair)이 아니라 클러스터가 진짜 위험이다.** A~B 0.93, B~C 0.93, A~C 0.40 이면 쌍 단위 위반은 0건인데
세 업체가 한 venue 로 뭉친다. REQ-3 이 이 경로를 닫는다(완전 연결 + 크기 상한).

## 선행 조건 — F2 스키마 개정 (미충족 시 착수 금지)

`source_record` 는 F2 REQ-6 에 의해 **append-only**(UPDATE·DELETE 거부)다. 따라서 소속 업체를
`source_record` 컬럼 갱신으로 표현할 수 없고 **별도 링크 테이블이 필수**다.

| 대상 | 필요 정의 | 근거 |
|---|---|---|
| `venue_source_link` | (venue_id FK, source_record_id FK, match_score numeric(4,3), match_evidence jsonb NOT NULL, resolver_version text NOT NULL, linked_at, unlinked_at NULL) — **행 UPDATE 는 unlinked_at 설정만 허용, DELETE 거부** | REQ-3·REQ-6·FORBID-3 |
| `venue_merge_candidate` | (a_source_record_id, b_source_record_id, match_score, match_evidence jsonb, status ENUM('pending','merged','rejected')) | REQ-1·FORBID-1 |
| F2 REQ-1 스냅샷 | 도메인 테이블 목록에 위 2개 추가 (현행 "정확히 7개" 문구 갱신) | F2 `test:schema` 통과를 위해 필수 |

**본 태스크는 마이그레이션을 작성하지 않는다.** 부족이 발견되면 코드를 쓰지 않고 F2 변경을 요청한 뒤 대기한다.

```yaml
# ─── 식별 ───────────────────────────────
id:            C5-ENTITY-RESOLUTION
title:         엔티티 해소 (동일 업체 병합 · venue_source_link 생성)
workstream:    pipeline
owner_agent:   dev-pipeline

# ─── 존재 이유 ──────────────────────────
traces_to:     [H1, G4]
why:           "여러 소스의 같은 업체를 하나의 venue 로 묶지 못하면 가격 비교의 모수(업체 수)가 부풀려지고
                가격·태그가 서로 다른 행에 흩어져 C7 의 소스 교차 검증이 성립하지 않는다."

# ─── DAG ────────────────────────────────
depends_on:    [C1-CRAWLER-CORE, F2a-CORE-SCHEMA, C2-ADAPTER-NAVER, C3-ADAPTER-KAKAO]
blocks:        [C6-TAG-ASSIGN]
parallel_with: [C4-PRICE-NORMALIZER, W1-SEO-FOUNDATION]
gate:          [G1, G3]

# ─── 산출물 ─────────────────────────────
deliverable:
  pr_count:    1
  touches:
    - packages/pipeline/src/entity/**
    - packages/pipeline/tests/entity/**
    - packages/pipeline/fixtures/entity-eval/**
    - packages/pipeline/scripts/sample_entity_eval.py
  artifacts:
    - "블로킹 + 쌍 스코어링 + 클러스터 확정 3단 모듈"
    - "개발셋 200쌍 / 홀드아웃 100쌍 평가 데이터 + 표집 스크립트"
    - "match_evidence 스키마 및 병합 감사 로그"
    - "unlink(병합 해제) CLI 커맨드"

# ─── 요구사항 ───────────────────────────
requirements:
  - id: REQ-1
    statement: >
      홀드아웃 평가셋의 '다른 업체 쌍' 50건 중 자동 병합된 건수(false merge)가 0 이다.
    acceptance: "`pnpm test:entity-holdout` 내 falseMerge assertion === 0 (임계 하드코딩)"

  - id: REQ-2
    statement: >
      홀드아웃 평가셋의 '동일 업체 쌍' 50건에 대한 자동 병합률(recall)이 ≥ 0.85 이다.
    acceptance: "`pnpm test:entity-holdout` 내 recall assertion >= 0.85"

  - id: REQ-3
    statement: >
      자동 확정된 모든 클러스터는 (a) 내부 **모든 쌍**의 match_score ≥ 0.92 인 완전 연결이고,
      (b) 크기 ≤ 6 이다. 두 조건 중 하나라도 위배되는 클러스터는 자동 확정 대신
      구성 쌍 전체가 venue_merge_candidate 로 적재된다.
    acceptance: >
      속성 테스트 `pnpm test:entity-cluster` — 전이 픽스처(A~B 0.93, B~C 0.93, A~C 0.40) 포함
      200 클러스터 생성 후 완전 연결 위반 0건 · 크기 > 6 확정 클러스터 0건 ·
      해당 전이 픽스처의 3개 소스가 서로 다른 venue 로 남고 큐 적재 3쌍 존재.

  - id: REQ-4
    statement: >
      블로킹(후보 생성) 단계의 재현율이 ≥ 0.95 이다 — 홀드아웃 '동일 업체 쌍' 50건 중
      후보쌍 집합에 포함되지 못한 건이 2건 이하다.
    acceptance: >
      `pnpm test:entity-blocking` — 평가 쌍을 후보로 미리 주입하지 않고 전체 source_record 모집단에서
      블로킹을 실행한 뒤 포함 여부를 판정. 미포함 3건 이상이면 exit 1.

  - id: REQ-5
    statement: >
      평가 데이터는 `sample_entity_eval.py` 로 C2·C3 가 실제 수집한 source_record 에서
      블로킹 후보 층화 무작위 추출(시드 고정)되며, 개발셋 200쌍과 **개발 중 열람이 차단된 홀드아웃 100쌍**으로
      분리되고, 각 쌍의 정답 판단 근거(무엇을 보고 동일/상이로 판정했는지)가 기록된다.
    acceptance: >
      CI job `entity-eval-integrity` — (a) 표집 스크립트 재실행 결과의 쌍 id 집합이 커밋본과 일치,
      (b) 홀드아웃 경로가 `src/entity/**` 에서 참조 0건, (c) rationale 빈 값 0건,
      (d) 홀드아웃 100쌍 중 동일/상이 각 50쌍 구성 확인.

  - id: REQ-6
    statement: >
      병합·해제 전후 source_record 행 수와 raw_payload 체크섬 변화가 0 이고,
      `pipeline entity:unlink --venue-id=<id>` 왕복(merge→unlink) 후 해당 source_record 들이
      각각 단독 venue 로 복원된다.
    acceptance: >
      통합테스트 — 20건 왕복 후 raw_payload 해시 20/20 일치, source_record COUNT 변화 0,
      venue_source_link 의 이력 행(unlinked_at 이 채워진 행)이 보존됨을 assert.

  - id: REQ-7
    statement: >
      source_record 입력 순서를 100회 셔플해도 최종 클러스터 그룹핑 결과가 동일하다.
    acceptance: "`pnpm test:entity-determinism` — 100회 셔플 결과 그룹 서명 해시 전부 일치"

  - id: REQ-8
    statement: >
      C2·C3 가 실제 수집한 source_record 500건을 입력한 nightly 스모크에서
      서로 다른 소스 2개 이상이 연결된 venue 가 40개 이상 생성된다.
    acceptance: >
      CI job `entity-smoke` (스테이징 DB, nightly) — 해당 venue 수 < 40 이면 exit 1 및
      클러스터 크기 분포를 stdout 출력. 픽스처로는 만족 불가(입력이 DB 질의로 고정).

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when:     >
      후보쌍의 match_score 가 자동 병합 임계(0.92) 미만이거나, 클러스터가 REQ-3 의 완전 연결·크기 상한을
      위배하는 경우
    must_not: >
      venue_source_link 를 생성 (강제 병합 플래그·리커버리 재시도 등 우회 경로 포함)
    because:  >
      다른 업체가 병합되면 A업체 상세에 B업체의 회당 단가와 전화번호가 표시되고, 업체 미접촉 방침상
      발견 경로가 W7 신고뿐이라 오류가 수개월간 노출된다
    detect:   >
      `pnpm test:entity-cluster` 와 회색지대(0.75~0.92) 픽스처 40쌍에서 링크 생성 0건 · 큐 적재 40건 검증 +
      CI grep 으로 `force_merge` / `skip_threshold` 심볼 부재 확인
    on_violation: block_merge

  - id: FORBID-2
    when:     >
      두 레코드의 전화번호가 일치하고 그 번호가 대표번호 패턴
      (1544 / 1588 / 1600 / 1661 / 1670 / 080 시작)에 해당하는 경우
    must_not: >
      전화번호 신호에 가중치 0 이외의 값을 적용
    because:  >
      프랜차이즈 대표번호 하나로 강남·서초·송파의 전 지점이 한 업체로 뭉치면 지점별 가격이 서로 덮어써서
      '지역 × 카테고리' 비교가 통째로 무의미해진다
    detect:   >
      단위테스트 — 대표번호 픽스처 12쌍에서 match_evidence.phone.weight === 0 이고 링크 생성 0건 검증
    on_violation: block_merge

  - id: FORBID-3
    when:     >
      병합·재병합·해제 트랜잭션을 실행할 때
    must_not: >
      source_record 에 대해 UPDATE·DELETE 를 시도하거나, venue_source_link 의 기존 행을
      물리 삭제(해제는 unlinked_at 설정으로만 표현)
    because:  >
      오병합이 뒤늦게 발견돼도 원본과 링크 이력이 없으면 복원이 불가능하고, 소스가 재크롤을 막거나
      페이지를 내린 경우 그 업체 데이터는 영구 손실된다
    detect:   >
      통합테스트 — (a) source_record UPDATE/DELETE 시도 시 F2 append-only 트리거 예외 발생 확인,
      (b) 해제 후 링크 이력 행 수 감소 0건, (c) CI grep 으로 `DELETE FROM venue_source_link` 패턴 차단
    on_violation: block_merge

  - id: FORBID-4
    when:     >
      두 레코드의 좌표 거리가 ≤ 30m 이면서 정규화 상호명 유사도가 < 0.6 인 경우
    must_not: >
      좌표 근접 신호만으로 match_score 를 0.92 이상으로 산출
    because:  >
      강남 상가 빌딩은 층마다 다른 업체(3층 필라테스 / 5층 마사지 / 7층 한의원)가 들어차 있어,
      좌표 근접을 강한 신호로 쓰면 한 건물이 통째로 한 업체가 된다
    detect:   >
      단위테스트 — 동일 건물 다른 업체 픽스처 15쌍에서 match_score < 0.92 이고 링크 생성 0건 검증
    on_violation: block_merge

  - id: FORBID-5
    when:     >
      후보쌍의 두 레코드 **중 하나 이상**의 category 가 medical_wellness 인 경우
    must_not: >
      일반 축과 동일한 임계(0.92)로 자동 병합 (해당 쌍은 score ≥ 0.98 이면서 기관명 완전일치 또는
      사업자등록번호 일치가 있을 때만 자동 병합)
    because:  >
      서로 다른 의원의 비급여 진료비·진료과목이 한 페이지에 섞이면 의료광고법상 허위·과장 정보 제공에
      해당하고, 해당 의료기관의 정정 요구와 법적 분쟁 대상이 된다. 한쪽만 medical 로 분류된
      오분류 쌍(도수치료 ↔ 필라테스)이 가장 흔한 유입 경로다
    detect:   >
      단위테스트 — 한쪽만 medical 인 픽스처 10쌍 + 양쪽 medical 인 픽스처 10쌍 중 score 0.92~0.98 구간
      전량이 링크 생성 0건 · 큐 적재됨을 검증
    on_violation: block_merge

  - id: FORBID-6
    when:     >
      `pnpm test:entity-holdout` · `test:entity-blocking` · `entity-eval-integrity` 중 하나가 실패한
      상태에서 통과시키려는 변경을 만들 때
    must_not: >
      임계 상수(회색지대 하한 0.75 / 자동병합 0.92 / medical 0.98 / 클러스터 크기 상한 6 /
      블로킹 재현율 0.95)를 완화하거나, 평가 쌍의 정답 라벨 수정 · 홀드아웃 쌍 삭제 ·
      홀드아웃을 소스에서 참조
    because:  >
      precision 임계는 '틀린 병합을 얼마나 감수할지'에 대한 제품 결정이며, 시험지 쪽을 고쳐 통과시키면
      오병합이 측정되지 않은 채 공개 데이터로 흘러간다
    detect:   >
      CI job `entity-eval-integrity` — 임계 상수 파일과 `fixtures/entity-eval/**` diff 감지 시
      `eval-change-approved` 라벨 없이 머지 차단 (CODEOWNERS 병행)
    on_violation: block_merge
```
