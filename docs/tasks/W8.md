# W8 — 요청 처리 파이프라인 (접수 → 검토 → visibility 전환 → 회신)

> 신설 (감사 `docs/audit/W1-O3-audit.md` W7 절 A · 전체요약 E).
> **W7 은 접수만 하고, O2 큐는 C7 이 비공개 판정한 레코드 전용이다.** 두 계약을 100% 준수한 상태에서
> 삭제 요청이 DB 에 쌓이고 `correction_overdue` 만 올라간 채 처리할 UI·API·담당자가 배치 전체에 존재하지 않는다.
> 접수 기록은 남고 처리 기록은 없는 상태는 방어가 아니라 **방치의 증거**다. 본 태스크가 그 공백을 소유한다.
>
> **구조 전제 (DAG 정정 #2·#4):** 최종 공개 상태는 **C7 판정 컬럼 ⊕ 서프레션/오버라이드 레이어**를 `public_venue`
> 뷰가 결합해 산출한다. W8 은 `venue_suppression` 에만 쓰고 `venue.visibility` 에는 절대 쓰지 않는다.

```yaml
# ─── 식별 ───────────────────────────────
id:            W8-CORRECTION-PROCESSING
title:         정보 수정·삭제 요청 처리 파이프라인 (SLA 계측 포함)
workstream:    web
owner_agent:   dev-web

# ─── 존재 이유 ──────────────────────────
traces_to:     [H1, S5, KM-price-coverage]
why:           "접수된 삭제·정정 요청을 사람이 판단해 종결하는 경로가 없으면 W7 은 방치 이력만 축적하는 법적 부채가 되고, 정정 결과가 데이터에 반영되지 않아 H1 가격 커버리지의 오류가 영구히 남는다."

# ─── DAG ────────────────────────────────
depends_on:    [W7-CORRECTION-REQUEST, C7-QUALITY-GATE, F2b-QUALITY-SCHEMA]
blocks:        []
parallel_with: [O2-REVIEW-ADMIN, O1-METRICS-DASHBOARD]
gate:          null    # 법적 안전판이므로 게이트 뒤로 미루지 않는다. C7 뷰 의존은 depends_on 으로 강제

# ─── 산출물 ─────────────────────────────
deliverable:
  pr_count:    1
  touches:
    - apps/web/src/app/(internal)/corrections-queue/**
    - apps/web/src/app/api/internal/corrections/**
    - apps/web/src/lib/correction-processing/**
    - apps/web/tests/correction-processing/**
    - apps/web/fixtures/correction-processing/**
  artifacts:
    - "요청 처리 큐 화면 (due_at 오름차순 · 유형 필터)"
    - "처리 액션 API 4종 (승인-비공개 / 정정 / 반려 / 서프레션 해제)"
    - "venue_suppression 기록·해제 어댑터 (visibility 직접 쓰기 없음)"
    - "회신 발송기 + 발송 로그"
    - "SLA 지표 (유형별 처리 소요 p50/p90 · 기한 내 종결률 · overdue 잔량)"

# ─── 요구사항 ───────────────────────────
requirements:
  - id: REQ-1
    statement: >
      처리 큐는 status in (received, in_review) 인 요청을 due_at 오름차순으로, 유형 필터와 함께
      페이지당 50건 표시하며, requires_takedown_review=true 건을 목록 최상단 그룹으로 분리한다.
    acceptance: >
      e2e 테스트 — 픽스처 120건(takedown 5 · 트리아지 3 포함) 입력 시 3페이지, 1페이지 상단 8행이
      takedown/트리아지 건, 나머지는 due_at 오름차순.

  - id: REQ-2
    statement: >
      takedown 승인 시 venue_suppression 에 (venue_id, reason ∈ {request, legal}, actor_id,
      correction_request_id, created_at) 1행이 기록되고, 그 결과 public_venue 뷰에서 해당 업체 조회
      결과가 0건이 된다.
    acceptance: >
      통합테스트 — 승인 API 호출 후 (a) venue_suppression 1행, (b) public_venue 조회 0건,
      (c) venue.visibility 컬럼 값 변화 0건 assert.

  - id: REQ-3
    statement: >
      서프레션 해제(철회) 액션이 존재하며, 해제 후 동일 업체가 public_venue 뷰에서 다시 1건으로
      조회된다(오처리 복구 경로).
    acceptance: >
      통합테스트 — 승인 → 해제 순서 실행 후 public_venue 조회 1건, venue_suppression 행이 삭제가 아닌
      released_at 기록으로 종결됨을 assert.

  - id: REQ-4
    statement: >
      처리 액션 4종(승인·정정·반려·해제) 각각은 correction_action_log 1행
      (actor_id, request_id, action, before, after, reason_code, note, created_at)을 남긴다.
    acceptance: >
      통합테스트 — 4액션 실행 후 로그 4행, before/after JSON 이 서로 다르며 actor_id 가 세션 사용자와 일치.

  - id: REQ-5
    statement: >
      요청 종결 시 status 가 resolved 또는 rejected 로 전이되고 resolution_note(20자 이상)와
      reason_code(폐쇄 enum)가 함께 기록되며, 둘 중 하나라도 없으면 422 를 반환한다.
    acceptance: >
      통합테스트 — note 19자 422, reason_code 누락 422, 정상 입력 200 및 status 전이 확인.

  - id: REQ-6
    statement: >
      contact_email 이 있는 요청은 종결 시 회신 1건이 발송되고 발송 로그 1행이 남으며,
      contact_email 이 없는 요청은 /corrections/status 조회 결과에 resolution_note 가 노출된다.
    acceptance: >
      통합테스트 — 이메일 보유 픽스처 종결 시 발송 로그 1행 및 메일러 호출 1회, 이메일 미보유 픽스처
      종결 시 상태 조회 응답에 resolution_note 포함.

  - id: REQ-7
    statement: >
      SLA 지표로 유형별 처리 소요시간 p50/p90(시간), 기한 내 종결률, overdue 잔량을 내부 메트릭으로
      노출한다.
    acceptance: >
      통합테스트 — 픽스처(종결 10건: 소요 1~20시간, overdue 3건) 입력 시 p50/p90/종결률/잔량이
      기대값과 일치.

  - id: REQ-8
    statement: >
      스테이징에서 실제 접수 1건을 접수 → 승인 → public_venue 조회 0건 → 회신 로그 1행까지
      종단 처리하는 e2e 시나리오가 성공한다.
    acceptance: >
      `pnpm test:e2e:correction-flow-staging` — 4단계 assert 전부 통과 (픽스처 전용 실행은 실패로 간주).

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when:         takedown 승인 또는 정정 반영을 처리하는 코드 경로에서 공개 상태를 바꾸려는 경우
    must_not:     venue.visibility 컬럼이나 C7 판정 컬럼(quality_score·reason_codes)에 직접 쓰기
    because:      C7 은 "공개 판정 쓰기 경로가 정확히 1개"를 전제로 만들어졌다. 두 번째 쓰기 경로가 생기면 C7 이 다음 주기에 재판정하면서 삭제 요청으로 내린 업체를 다시 공개로 되돌리고, 그 사실을 아무도 관측하지 못한 채 법적 요구가 무효화된다
    detect:       CI 정적 검사 — 본 태스크 touches 내 `venue.visibility` / quality 컬럼 대상 UPDATE·ORM 호출 0건 + 통합테스트로 C7 게이트 재실행 후에도 public_venue 조회가 0건으로 유지됨을 assert
    on_violation: block_merge

  - id: FORBID-2
    when:         요청 유형이 price_error 또는 info_error 이고 requires_takedown_review=false 인 경우
    must_not:     업체 전체를 숨기는 서프레션 기록으로 처리
    because:      한 줄의 가격 오류를 업체 전체 비공개로 해결하면 요청 1건마다 커버리지가 깎여 H1(가격 커버리지 40%)이 운영 행위로 무너지고, 사용자에게는 정정이 아니라 정보 소실로 나타난다
    detect:       통합테스트 — price_error/info_error 픽스처 처리 시 venue_suppression 행 증가 0건이며 정정은 오버라이드 레이어에만 기록됨을 assert
    on_violation: block_merge

  - id: FORBID-3
    when:         now > due_at 인 요청을 처리·종결하는 경우
    must_not:     due_at 을 미래로 연장하거나 resolution_note 없이 status 를 resolved 로 전이
    because:      기한 초과 건을 데이터 수정으로 지우면 SLA 지표는 통과하지만 실제 방치는 그대로 남고, 분쟁 시 "지표상 문제없었다"는 주장이 로그 diff 하나로 무너져 방어가 오히려 불리해진다
    detect:       DB 트리거 + 통합테스트 — correction_request.due_at 의 UPDATE 시도가 거부되고, resolution_note NULL 로는 resolved 전이가 422 임을 assert
    on_violation: block_merge

  - id: FORBID-4
    when:         종결 회신 메일을 렌더·발송하는 경우
    must_not:     본문·헤더에 다른 요청자의 정보, 내부 판단 로그(actor_id·내부 메모), 업체 연락처를 포함하거나 수신자를 2명 이상으로 설정
    because:      정정 요청자에게 보내는 단 한 통의 메일에 타인의 접수 내용이 섞이면 그 자체가 개인정보 유출 사고이며, 신고 대상이 되는 순간 창구 운영이 중단된다
    detect:       단위테스트 — 회신 템플릿 렌더 결과에 금지 키(actor_id, internal_note, venue_phone) 0건, 수신자 배열 길이 1 assert
    on_violation: block_merge

  - id: FORBID-5
    when:         정정 요청 내용을 데이터에 반영하는 경우
    must_not:     source_record 원문(raw_payload)을 수정·삭제하거나 크롤링 파이프라인의 파싱 결과를 직접 덮어쓰기
    because:      원문이 훼손되면 다음 수집 주기에 정정이 사라져 같은 요청이 반복 접수되고, "이 가격은 언제 어디서 왔는가"를 증명할 근거가 없어져 재요청 시 대응이 불가능해진다
    detect:       통합테스트 — 정정 처리 전후 source_record 행 수·raw_payload 해시 불변 assert + CI 정적 검사로 source_record 대상 UPDATE/DELETE 0건
    on_violation: block_merge

  - id: FORBID-6
    when:         처리 액션 트랜잭션에서 correction_action_log insert 가 실패한 경우
    must_not:     요청 상태 전이나 서프레션 기록을 커밋 (별도 트랜잭션·비동기 기록으로 분리하는 것 포함)
    because:      처리 이력 없는 비공개 전환은 "누가 왜 이 업체를 내렸는가"를 증명하지 못하게 만들고, 오처리로 매출 손해를 주장하는 업체의 이의 제기에 방어할 수단이 사라진다
    detect:       통합테스트 — 로그 insert 실패를 주입한 상태에서 액션 요청 시 status·venue_suppression 이 모두 롤백되고 5xx 를 반환함을 assert
    on_violation: block_merge

  - 업체에게 먼저 연락하는 아웃바운드 (업체 미접촉 방침 — 회신은 요청자에게만)

rollback: >

  public_venue 조회로 확인하고, (b) 미처리 요청은 수동 처리 절차로 전환한 사실을 운영 로그에 남긴다.

done_when:
  - REQ-1~REQ-8 acceptance 가 CI 에서 전부 통과

  - C7 게이트를 재실행해도 서프레션된 업체가 public_venue 에 복귀하지 않음을 확인 (FORBID-1)

  - touches 밖 파일 변경 0건 (CI path guard 통과)
```
