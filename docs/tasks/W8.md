# W8 — 요청 처리 파이프라인 (접수 → 검토 → 비공개 전환 → 회신)

> 개정 3판 (2차 감사 `docs/audit/round2-webops.md` W8 절 · F2b/F2c 개정 반영)
> 2차 감사 판정은 *"처리했다고 기록하면서 실제로는 아무것도 내리지 않는다"* 였고 원인은 `venue_suppression` 이
> `public_venue` 에 결합되지 않는다는 것이었다. **F2b 개정(뷰 결합 + force_public ⊂ hidden_quality)으로 해소되어
> takedown 실행 경로가 열렸다.** 이번 개정은 (a) 컬럼·해제 표현을 F2b 이벤트 로그 정본(action='suppress'/'lift')에 맞추고,
> (b) 로그·요청 테이블 소유를 **F2c-OPS-LEGAL-SCHEMA** 로 이관하며, (c) 벌크 종결 경로를 막는다.

## 선행 조건 — 상류 계약 개정 (미충족 시 착수 금지)

| # | 필요한 것 | 소유 계약 | 현재 상태 | 확인 방법 |
|---|---|---|---|---|
| 1 | `public_venue` 뷰가 `venue_suppression` 을 결합해 **활성 억제(최신 행 action='suppress') 업체를 항상 제외** | F2b-QUALITY-SCHEMA | **해소됨** — F2b REQ-4 (1)·FORBID-1 반영 | `pnpm test:public-view` — suppress INSERT 직후 조회 0건 |
| 2 | `hidden_legal`·`hidden_request`·활성 억제는 `force_public` 으로 뒤집히지 않음 (force_public ⊂ hidden_quality) | F2b-QUALITY-SCHEMA | **해소됨** — F2b REQ-3·REQ-4 (c)·FORBID-4 반영 | `pnpm test:public-view` REQ-4 (c) 3케이스 0건 |
| 3 | C7 REQ-4 의 `REQUEST_TAKEDOWN` 전이 주체를 **서프레션 기록 기반**으로 표기 | C7-QUALITY-GATE | 확인 필요 — W8 은 `venue.visibility` 에 쓰지 않는다 | C7 계약 본문에 "전이는 venue_suppression 기록으로 표현" 명시 |
| 4 | `ops.correction_action_log`(id, request_id, actor_id, action, before, after, reason_code, note, created_at) + `correction_request.resolution_note`·`reason_code` + `due_at` UPDATE 거부 트리거 | **F2c-OPS-LEGAL-SCHEMA** | **계약상 존재** (F2c REQ-1·REQ-2·REQ-3) | `pnpm test:schema-ops` · `pnpm test:append-only-ops` 통과 |
| 5 | 쓰기/조회 함수 `suppressVenue` · `liftSuppression` · `listCorrectionQueue` · `closeCorrectionRequest` | F5-API-LAYER | 부재 | `packages/api` export 존재 |

> 1·2 는 F2b 개정으로 해소되어 **takedown 실행 경로가 열렸다.** 착수 시 두 테스트가 실제로 존재하는지 먼저 확인한다 —
> 결합이 없는 상태로 착수하면 "처리했다는 기록만 남고 업체는 계속 공개되는" 구현이 만들어지고,
> 접수·처리 이력이 모두 남은 채 이행되지 않은 상태는 아무 기록도 없는 것보다 법적으로 불리하다.

  - id: REQ-4
    statement: >
      처리 액션 4종(승인·정정·반려·해제) 각각은 ops.correction_action_log 1행

forbid:
  - id: FORBID-1
    when:         takedown 승인 또는 정정 반영을 처리하는 코드 경로에서 공개 상태를 바꾸려는 경우

    detect:       CI 정적 검사(본 태스크 touches 내 visibility·quality 컬럼 UPDATE·ORM 호출 0건) + 통합테스트로 C7 게이트 재실행 후에도 public_venue 조회가 0건 유지 assert

    must_not:     due_at 을 미래로 연장하거나, 동일 문자열 resolution_note 로 일괄 종결하거나, 21건째 이후를 추가 확인 없이 수락
    because:      기한 초과 건을 데이터 수정이나 일괄 종결로 지우면 SLA 지표는 녹색이 되지만 실제 방치는 그대로 남고, 분쟁 시 "지표상 문제없었다"는 주장이 로그 diff 하나로 무너져 방어가 오히려 불리해진다
    detect:       DB 트리거(due_at UPDATE 거부) + 통합테스트 — (a) resolution_note NULL·중복 문자열 종결이 422, (b) 60분 창 21번째 종결 요청이 429 이고 해당 요청이 미종결로 남음 assert
    on_violation: block_merge

    when:         종결 회신 메일을 렌더·발송하는 경우

    detect:       단위테스트 — 템플릿 렌더 결과에 금지 키(actor_id·internal_note·venue_phone) 0건, 수신자 배열 길이 1 assert
    on_violation: block_merge

    detect:       통합테스트(처리 전후 source_record 행 수·raw_payload 해시 불변) + CI 정적 검사로 해당 테이블 UPDATE/DELETE 0건

  - id: FORBID-6

    detect:       통합테스트 — 로그 insert 실패 주입 상태에서 액션 요청 시 status·서프레션이 모두 롤백되고 5xx 를 반환함을 assert
    on_violation: block_merge
