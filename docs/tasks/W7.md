# W7 — 정보 수정·삭제 요청 **접수** 폼

> 개정 2판 (감사 `docs/audit/W1-O3-audit.md` W7 절 반영)
> 주요 변경: 처리 경로를 **W8-CORRECTION-PROCESSING 으로 귀속**하고 `blocks` 정합화 · traces_to 에 가설 추가 ·
> overdue 보호 범위를 전 유형으로 확대 · `other` 유형의 삭제 요구 트리아지 REQ 신설 ·
> 파기 배치의 스케줄 등록·실행 증적 요구 · 정상 접수 커버리지 REQ(원칙 2.5) · gate 에서 G2 제거

```yaml
# ─── 식별 ───────────────────────────────
id:            W7-CORRECTION-REQUEST
title:         정보 수정·삭제 요청 접수 폼 (업체 미접촉 방침의 유일한 예외 창구)
workstream:    web
owner_agent:   dev-web

# ─── 존재 이유 ──────────────────────────
traces_to:     [H1, S5, KM-price-coverage]
why:           "업체 접촉 없이 공개 정보만으로 운영하는 구조에서 오류 정정·삭제 요구를 받을 창구가 없으면 첫 분쟁이 곧바로 서비스 중단 요구가 되고, 동시에 price_error 요청은 H1 '가격 확인됨' 판정의 오류율을 관측하는 유일한 외부 피드백이다."

# ─── DAG ────────────────────────────────
depends_on:    [W1-SEO-FOUNDATION, F5-API-LAYER, F2b-QUALITY-SCHEMA]
blocks:        [W8-CORRECTION-PROCESSING]
parallel_with: [W2-DISCOVERY-LIST, W3-VENUE-DETAIL, W5-EDITOR-REPORT]
gate:          null      # 공개 페이지가 서비스되는 시점부터 필요. SEO 게이트(G2) 뒤에 둘 근거가 없다

# ─── 산출물 ─────────────────────────────
deliverable:
  pr_count:    1
  touches:
    - apps/web/src/app/(public)/corrections/**
    - apps/web/src/components/correction/**
    - apps/web/src/app/api/corrections/**
    - apps/web/src/lib/correction/**
    - ops/schedules/purge-correction-contact.yml
    - apps/web/tests/correction/**
    - apps/web/fixtures/correction/**
  artifacts:
    - "요청 폼 페이지 + 접수 API (유형 4종 · 접수코드 발급)"
    - "삭제 요구 키워드 트리아지 모듈"
    - "상태 조회 페이지 /corrections/status"
    - "correction_overdue{type} 내부 메트릭 핸들러"
    - "연락처 파기 배치 + 스케줄 등록 파일"

# ─── 요구사항 ───────────────────────────
requirements:
  - id: REQ-1
    statement: >
      요청 폼은 유형 4종(price_error, info_error, takedown, other) 중 정확히 1개 선택을 필수로 하고,
      대상 venue_id 를 자동 첨부해 correction_request 레코드 1건을 생성한다.
    acceptance: >
      e2e 테스트 — 4유형 각각 제출 시 레코드 4건 생성, 유형 미선택 제출은 422 및 레코드 0건.

  - id: REQ-2
    statement: >
      접수 레코드는 status(received|in_review|resolved|rejected)와 due_at 을 가지며, due_at 은
      takedown 유형이면 접수 +7일, 그 외 유형은 접수 +14일이다.
    acceptance: >
      단위테스트 — 유형 4종의 due_at 계산값이 고정 시각 mock 기준 기대치와 일치.

  - id: REQ-3
    statement: >
      type=other 또는 type=info_error 로 접수된 요청의 본문이 삭제 요구 키워드 사전(삭제·내려·비공개·
      게시중단·법적조치 등 12개 표제어)에 매치되면 requires_takedown_review=true 로 표시되고 due_at 이
      접수 +7일로 단축된다.
    acceptance: >
      단위테스트 — 키워드 포함 본문 12건 전부 플래그 true 및 due_at +7일, 미포함 본문 12건 전부 false.

  - id: REQ-4
    statement: >
      제출 성공 시 128bit 랜덤 접수코드를 화면에 표시하고, /corrections/status?code= 로 status 와
      due_at 을 조회할 수 있다.
    acceptance: >
      e2e 테스트 — 제출 후 코드 조회 시 status=received 렌더, 잘못된 코드 404. 스테이징 배포에서
      실제 제출 1건 → 코드 조회 200 스모크 포함.

  - id: REQ-5
    statement: >
      정상 제출 골든 20건(이메일 포함 10건 · 공란 10건, 민감정보 패턴 없음)의 접수 성공률이 100%이며,
      저장된 본문이 입력 본문과 문자 단위로 일치한다.
    acceptance: >
      통합테스트 `pnpm test:correction-golden` — 20건 전부 201, 본문 diff 0건 (전량 거부·전량 마스킹
      구현 시 실패).

  - id: REQ-6
    statement: >
      동일 IP 해시 기준 1시간 내 5건을 초과하는 제출은 429 를 반환하고, 5건 이하는 전부 수락된다.
    acceptance: >
      통합테스트 — 동일 IP 6회 연속 제출 시 1~5번째 201, 6번째 429, 저장 레코드 5건.

  - id: REQ-7
    statement: >
      status in (received, in_review) 이고 now > due_at 인 요청 수가 유형별로
      correction_overdue{type} 메트릭에 노출된다.
    acceptance: >
      통합테스트 — 기한 초과 픽스처(takedown 2건, other 1건, price_error 1건) 입력 시 메트릭 값이
      각각 2, 1, 1 로 반환.

  - id: REQ-8
    statement: >
      resolved/rejected 전이 후 30일이 지난 레코드의 contact_email 을 null 로 바꾸는 파기 배치가
      스케줄 파일에 일 1회로 등록되고, 실행마다 처리 건수를 purge_contact_runs 지표로 남긴다.
    acceptance: >
      (a) 단위테스트 — 29일/31일 경과 픽스처 실행 후 contact_email 유지/null, 본문·상태 이력 불변,
      (b) CI — ops/schedules 파일에 해당 잡이 존재하고 cron 표현식이 일 1회 이상임을 검사,
      (c) 스테이징 1회 실행 후 purge_contact_runs 값 ≥ 1.

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when:         type=takedown 이거나 requires_takedown_review=true 인 요청이 접수된 경우
    must_not:     대상 venue 의 `visibility` 를 변경하거나 venue_suppression 행을 생성하거나 status 를 resolved 로 자동 전이
    because:      자동 반영은 경쟁 업체·장난 요청 1건으로 정상 업체가 검색 결과에서 사라지게 만들고, 색인에서 빠진 페이지의 순위는 되돌려도 회복되지 않는다. 판단은 사람이 하는 W8 의 책임이다
    detect:       통합테스트 — takedown 접수 직후 venue.visibility 값 불변, venue_suppression 행 증가 0건, status=received 유지 assert
    on_violation: block_merge

  - id: FORBID-2
    when:         status in (received, in_review) 이고 now > due_at 인 요청이 유형과 무관하게 1건 이상 존재하는 경우
    must_not:     correction_overdue 메트릭을 0 으로 고정하거나 환경변수·플래그로 노출을 비활성화
    because:      방치된 삭제·정정 요구는 개인정보 분쟁조정·정보통신망법 민원으로 직행하며, "요청받고 며칠간 방치했다"는 타임스탬프가 반박 불가능한 증거로 남는다. takedown 으로만 보호 범위를 좁히면 사용자가 유형을 잘못 고른 삭제 요구가 보호 밖에 남는다
    detect:       통합테스트 — 유형 4종 각각의 overdue 픽스처 상태에서 메트릭 값 > 0 assert + 소스에 억제 플래그·상수 0 반환 경로 부재를 정적 검사
    on_violation: block_merge

  - id: FORBID-3
    when:         제출 본문 또는 이메일 필드가 주민등록번호·카드번호·휴대전화번호 정규식에 매치되는 경우
    must_not:     매치 구간을 원문 그대로 DB 컬럼 및 애플리케이션 로그에 저장
    because:      고유식별정보·민감정보 수집은 별도 동의 없이는 위법이고, 로그 백업까지 확산되면 파기 범위를 특정할 수 없어 정정 자체가 불가능해진다
    detect:       단위테스트 — 3개 패턴 포함 입력에서 저장값의 매치 구간만 마스킹되고 나머지 본문은 보존되며 로그 스냅샷에 원문이 부재함을 assert (REQ-5 골든 20건이 함께 통과해야 한다)
    on_violation: block_merge

  - id: FORBID-4
    when:         /corrections/status 조회 라우트가 요청 레코드를 식별하는 경우
    must_not:     접수코드 외의 파라미터(순번 id, venue_id, 이메일)로 레코드를 조회 가능하게 노출
    because:      순번 id 로 열람되면 제3자가 전체 요청 본문과 제출자 이메일을 순회 수집할 수 있고, 이는 그 자체로 신고 대상 개인정보 유출 사고가 된다
    detect:       통합테스트 — id/이메일/venue_id 파라미터 접근 3케이스 모두 404, 접수코드 엔트로피 ≥128bit assert
    on_violation: block_merge

  - id: FORBID-5
    when:         correction_request 레코드를 정리·삭제하는 코드 경로(운영 스크립트·배치 포함)를 추가하는 경우
    must_not:     요청 본문·접수시각·상태 이력을 물리 삭제 (REQ-8 의 contact_email NULL 갱신은 규칙 안의 예외로 허용한다)
    because:      "언제 접수해 언제 처리했는가"가 분쟁 시 유일한 방어 증거이며, 하드 삭제하면 정당하게 처리한 건조차 방치한 것으로 반증할 수 없다
    detect:       CI 정적 검사 — correction_request 대상 DELETE/TRUNCATE/destroy 호출 검출 시 exit 1 (contact_email 컬럼 UPDATE 는 allowlist) + 통합테스트로 파기 배치 실행 후 행 수 불변 assert
    on_violation: block_merge

# ─── 경계 ───────────────────────────────
out_of_scope:
  - 접수 이후의 검토·판단·`visibility` 전이·회신 — W8-CORRECTION-PROCESSING 소관
  - C7 품질 미달 레코드의 검수 큐 — O2-REVIEW-ADMIN 소관 (요청 큐와 별개)
  - 업체에게 발신하는 이메일·전화 등 아웃바운드 (업체 미접촉 방침)
  - 로그인·본인확인·사업자 증빙 업로드
  - 알림 룰·채널 연동 — O3 소관 (본 태스크는 메트릭 노출까지)
  - DB 스키마 변경 — F2b-QUALITY-SCHEMA 소관. correction_request 테이블이 없으면 착수를 중단하고 F2 변경을 요청한다

rollback: >
  PR revert 시 폼·접수 API·상태 조회가 제거된다. correction_request 테이블은 DROP 하지 않는다
  (접수 이력은 법적 증거). 파기 스케줄 파일도 함께 제거되므로 revert 기간 동안 연락처가 남는데,
  이는 30일 파기 의무 위반이 되므로 revert 시 수동 파기 1회를 실행하고 실행 로그를 남긴다.
  폼 제거 기간에는 대체 접수 경로(푸터의 문의 이메일 주소)를 유지한다.

done_when:
  - REQ-1~REQ-8 acceptance 가 CI 에서 전부 통과
  - FORBID-1~5 각각의 위반 픽스처가 커밋되고 detect 가 차단함을 PR 본문에 기록
  - 정상 골든 20건 접수 성공률 100% 확인 (전량 차단 구현 방지)
  - correction_overdue{type} 메트릭이 유형 4종 전부에 대해 조회 가능
  - F2 스키마에 correction_request 테이블과 requires_takedown_review 컬럼이 실재함을 확인 (없으면 F2 변경 선행)
  - touches 밖 파일 변경 0건 (CI path guard 통과)
```
