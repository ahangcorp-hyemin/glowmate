# W7 — 정보 수정·삭제 요청 **접수** 폼

> 개정 3판 (2차 감사 `docs/audit/round2-webops.md` W7 절 반영)
> 주요 변경: `correction_request` 스키마 부재를 **선행 조건 표**로 승격(착수 차단) · 접수 API 의 DB 쓰기를 **F5 경유**로 확정 ·
> **폼 도달 경로 REQ 신설** · 파기 조건에 **미처리 180일 분기** 추가 · **SLA 산정 상수 상향 금지 FORBID 신설** ·
> IP 해시 솔트 규정 · 알림 룰 파일 소유(O3 규약)

## 선행 조건 — 상류 계약 개정 (미충족 시 착수 금지)

| # | 필요한 것 | 소유 계약 | 현재 상태 | 확인 방법 |
|---|---|---|---|---|
| 1 | `ops.correction_request` — (id, venue_id, type, body, contact_email, access_code UNIQUE, status, due_at, requires_takedown_review, resolution_note, reason_code, created_at, closed_at) + type·status 폐쇄 ENUM + due_at UPDATE 거부 트리거 | **F2c-OPS-LEGAL-SCHEMA** | **계약상 존재** (F2c REQ-1·REQ-2) | `pnpm test:schema-ops` 통과 |
| 2 | 접수·조회 쓰기/읽기 함수 `createCorrectionRequest` · `getCorrectionRequestByCode` | F5-API-LAYER | **부재** (공개 조회 2종만) | `packages/api` export 존재 |
| 3 | 공개 라우트에서 정정 요청 폼으로 가는 진입 링크 (푸터) | W1-SEO-FOUNDATION (`app/layout.tsx` 소유) | 부재 — 상신 대상 | 빌드 HTML 에서 buildPath('correction') 링크를 포함한 라우트 ≥1 |

> 1·2 미충족 시 착수하지 않는다. `apps/web` 에서 DB 를 직접 import 하는 우회는 F5 `boundary` job 에 확정적으로 걸리며,
> 예외를 파는 순간 공개면 보호(F5 REQ-3)도 함께 협상 대상이 된다.

# ─── 요구사항 ───────────────────────────
requirements:
  - id: REQ-1
    statement: >
      요청 폼은 유형 4종(price_error, info_error, takedown, other) 중 정확히 1개 선택을 필수로 하고,
      대상 venue_id 를 자동 첨부해 F5 `createCorrectionRequest` 를 통해 `ops.correction_request` 레코드 1건을 생성한다.
    acceptance: >
      e2e — 4유형 각각 제출 시 레코드 4건, 유형 미선택 제출은 422 및 레코드 0건.
      `boundary` job 에서 apps/web 의 DB import 0건 유지.

  - id: REQ-2
    statement: >
      접수 레코드의 due_at 은 takedown 유형이면 접수 +7일, 그 외 유형은 접수 +14일이며 산정 상수는
      `apps/web/src/lib/correction/sla.ts` 1곳에만 선언된다.
    acceptance: >
      단위테스트 — 유형 4종의 due_at 이 고정 시각 mock 기준 기대치와 일치, CI grep 으로 상수 리터럴
      선언 위치가 1곳임을 assert.

  - id: REQ-3
    statement: >
      type=other 또는 info_error 로 접수된 요청의 본문이 삭제 요구 키워드 사전(12표제어)에 매치되면
      requires_takedown_review=true 로 표시되고 due_at 이 접수 +7일로 단축된다.
    acceptance: >
      단위테스트 — 키워드 포함 본문 12건 전부 플래그 true·due_at +7일, 미포함 12건 전부 false.

  - id: REQ-4
    statement: >
      제출 성공 시 128bit 랜덤 접수코드를 화면에 표시하고 /corrections/status?code= 로 status 와
      due_at 을 조회할 수 있다.
    acceptance: >
      e2e — 제출 후 코드 조회 시 status=received 렌더, 잘못된 코드 404. 스테이징 배포에서 실제 제출
      1건 → 코드 조회 200 스모크 포함.

  - id: REQ-5
    statement: >
      정상 제출 골든 20건(이메일 포함 10 · 공란 10, 민감정보 패턴 없음)의 접수 성공률이 100% 이며
      저장된 본문이 입력 본문과 문자 단위로 일치한다.
    acceptance: >
      `pnpm test:correction-golden` — 20건 전부 201, 본문 diff 0건 (전량 거부·전량 마스킹 구현 시 실패).

  - id: REQ-6
    statement: >
      동일 IP 해시(환경변수 솔트 결합) 기준 1시간 내 5건을 초과하는 제출은 429 를 반환하고 5건 이하는
      전부 수락되며, 원시 IP 는 저장되지 않는다.
    acceptance: >
      통합테스트 — 동일 IP 6회 제출 시 1~5번째 201·6번째 429, 저장 레코드 5건, 레코드·로그에

      correction_overdue{type} 메트릭에 노출되고, 그 메트릭을 참조하는 알림 룰 1종이

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when:         type=takedown 이거나 requires_takedown_review=true 인 요청이 접수된 경우
    must_not:     대상 venue 의 `visibility` 변경, venue_suppression 행 생성, status 의 resolved 자동 전이 중 어느 것도 수행
    because:      자동 반영은 경쟁 업체·장난 요청 1건으로 정상 업체를 검색 결과에서 지우고, 색인에서 빠진 페이지의 순위는 되돌려도 회복되지 않는다. 판단은 사람이 하는 W8 의 책임이다
    detect:       통합테스트 — takedown 접수 직후 venue.visibility 불변, venue_suppression 행 증가 0건, status=received 유지 assert
    on_violation: block_merge

  - id: FORBID-2
    when:         status in (received, in_review) 이고 now > due_at 인 요청이 유형과 무관하게 1건 이상 존재하는 경우
    must_not:     correction_overdue 메트릭을 0 으로 고정하거나 플래그·환경변수로 노출을 비활성화
    because:      방치된 삭제·정정 요구는 개인정보 분쟁조정·정보통신망법 민원으로 직행하며, "요청받고 며칠간 방치했다"는 타임스탬프가 반박 불가능한 증거로 남는다
    detect:       통합테스트 — 유형 4종 overdue 픽스처에서 메트릭 값 > 0 assert + 소스에 상수 0 반환·억제 플래그 경로 부재 정적 검사
    on_violation: block_merge

  - id: FORBID-3
    when:         SLA 산정 상수(REQ-2 의 +7일 / +14일) 또는 트리아지 키워드 사전(REQ-3 의 12표제어)을 변경하는 경우
    must_not:     기한을 늘리거나 키워드를 줄이는 방향의 변경을 라벨 `sla-change` 와 작성자 외 승인 없이 머지
    because:      overdue 지표를 0 으로 만드는 가장 빠른 방법은 처리를 잘하는 것이 아니라 기한을 늘리는 것이다. 레코드별 due_at 은 W8 FORBID-3 이 막지만 산정 상수를 바꾸면 신규 접수 전체의 기한이 조용히 늘어나 방치가 지표에서 사라진다
    detect:       CI — sla.ts·키워드 사전 파일 diff 에서 기한 증가·키워드 삭제를 파싱해 검출 시 라벨·승인자 조건 검사, 미충족이면 exit 1
    on_violation: block_merge

  - id: FORBID-4
    when:         제출 본문 또는 이메일 필드가 주민등록번호·카드번호·휴대전화번호 정규식에 매치되는 경우
    must_not:     매치 구간을 원문 그대로 DB 컬럼 및 애플리케이션 로그에 저장
    because:      고유식별정보·민감정보 수집은 별도 동의 없이는 위법이고, 로그 백업까지 확산되면 파기 범위를 특정할 수 없어 정정 자체가 불가능해진다
    detect:       단위테스트 — 3개 패턴 입력에서 매치 구간만 마스킹되고 나머지 본문은 보존되며 로그 스냅샷에 원문 부재 assert (REQ-5 골든 20건이 함께 통과해야 한다)
    on_violation: block_merge

  - id: FORBID-5
    when:         /corrections/status 조회 라우트가 요청 레코드를 식별하는 경우
    must_not:     접수코드 외의 파라미터(순번 id · venue_id · 이메일)로 레코드를 조회 가능하게 노출
    because:      순번 id 로 열람되면 제3자가 전체 요청 본문과 제출자 이메일을 순회 수집할 수 있고, 이는 그 자체로 신고 대상 개인정보 유출 사고가 된다
    detect:       통합테스트 — id/이메일/venue_id 파라미터 접근 3케이스 모두 404, 접수코드 엔트로피 ≥128bit assert
    on_violation: block_merge

  - id: FORBID-6
    when:         ops.correction_request 레코드를 정리·삭제하는 코드 경로(운영 스크립트·배치 포함)를 추가하는 경우
    must_not:     요청 본문·접수시각·상태 이력을 물리 삭제 (REQ-8 의 contact_email NULL 갱신은 규칙 안의 예외)
    because:      "언제 접수해 언제 처리했는가"가 분쟁 시 유일한 방어 증거이며, 하드 삭제하면 정당하게 처리한 건조차 방치한 것으로 반증할 수 없다
    detect:       CI 정적 검사 — 해당 테이블 대상 DELETE/TRUNCATE/destroy 호출 검출 시 exit 1(contact_email UPDATE 는 allowlist) + 통합테스트로 파기 배치 실행 후 행 수 불변 assert
    on_violation: block_merge
