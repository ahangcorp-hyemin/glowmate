> **개정 2 (감사 반영)** — `docs/audit/C1-C7-audit-full.md` §1 필수 수정 5건 반영.
> 주요 변경: ID 정정 · 실수집 스모크 REQ 신설(R-7) · allowlist diff 라벨 게이트 · 원문 삭제 조건부 예외 편입 ·

      500 job 부하 테스트에서 host별 1초 슬라이딩 윈도우 요청수 > max_rps(allowlist 값, 기본 0.5)

      (c) robots.txt 취득 실패(타임아웃·4xx·5xx) 세 경우 각각에서 아웃바운드 요청 0건으로 job을

      레지스트리)을 패키지 외부에서 import 가능한 고정 경로로 제공하며, 레퍼런스 더미 어댑터는
      `services/crawler/adapters/<source_id>/adapter.py` 파일 추가만으로 (core/ · pyproject.toml · 타 어댑터
      디렉토리 diff 0) 등록되어 adapter_contract_suite 15개 케이스를 skip 0건으로 통과한다.
    acceptance:
      - "`pytest services/crawler/tests/core/test_adapter_contract.py` — passed=15, skipped=0"

  - id: REQ-7

      실패시키는 시나리오에서 워커 프로세스 비정상 종료 0회, 동일 source 연속 10회 실패 시 해당

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when: >
      (a) enqueue 대상 URL의 host가 sources.allowlist.yaml에 없거나 approved=false 인 경우, 또는
      (b) PR diff가 sources.allowlist.yaml 의 approved · max_rps · per_host_concurrency 값을 변경하는 경우
    must_not: >
      (a) 해당 URL을 큐에 적재하거나 allowlist 검사를 우회하는 테스트·백필 플래그를 추가,
      (b) `d3-change-approved` 라벨과 D3 산출물(verdicts.csv · crawl_policy.yaml) 갱신 없이 머지
    because: >
      D3 실사를 거치지 않은 사이트를 긁으면 G3 통과 판정 자체가 무효가 되고, 수집이 느리다는 이유로
      allowlist의 max_rps 숫자만 올리는 것이 가장 싼 지름길인데 그 변경은 코드 diff 없이 대상 서버 부하를
      즉시 배가시킨다. ToS 위반 통지 한 건이면 파이프라인 전체를 정지하고 수집 원문까지 폐기해야 한다.
    detect: >
      (a) 단위테스트 test_preflight_gate — 미등재 host 20건 입력 시 큐 적재 0건·요청 0건 assert.
      (b) CI job `allowlist-guard` — sources.allowlist.yaml diff 감지 시 `d3-change-approved` 라벨 존재 검사 +
      각 항목의 max_rps ≤ docs/discovery/D3/crawl_policy.yaml 의 max_requests_per_min/60,
      per_host_concurrency ≤ max_concurrency, approved=true 인 source 가 verdicts.csv 에서 verdict ≠ forbidden 임을 대조.
    on_violation: block_merge

  - id: FORBID-2
    when:         "robots.txt 취득이 타임아웃·4xx·5xx로 실패한 경우"
    must_not:     "robots 규칙을 '제한 없음'으로 간주하고 요청을 전송 (fail-open)"
    because: >
      실사 시점에 Allow였던 경로가 사이트 개편으로 Disallow가 되어도 서버 장애 몇 분 동안 fail-open이
      발동하면 금지 경로를 대량으로 긁게 되고, 이 기록은 상대 서버 로그에 남아 사후 방어가 불가능하다.
    detect:       "단위테스트 test_preflight_gate — robots 503/타임아웃/커넥션 리셋 3개 픽스처에서 mock transport 호출 0회 assert"
    on_violation: block_merge

  - id: FORBID-3
    when: >
      특정 host에 대해 최근 1초 내 요청수가 max_rps에 도달했거나 in-flight 요청이 per_host_concurrency에
      도달한 상태
    must_not: >
      재시도·백필·수동 트리거를 사유로 추가 요청을 디스패치하거나, 코드·환경변수에서 allowlist 기재
      상한보다 큰 값으로 오버라이드
    because: >
      재시도 폭주가 rate limiter를 우회하면 대상 사이트에 사실상 부하 공격이 되어 IP 차단 → 이후 어떤
      소스에서도 가격을 못 모으고 H1 검증 자체가 중단된다.
    detect: >
      부하테스트 test_rate_limit_window(request_log 슬라이딩 윈도우 위반 0건) +
      설정 로더 단위테스트(allowlist 상한 초과 오버라이드 시 ValueError)
    on_violation: block_merge

  - id: FORBID-4
    when: >
      응답이 (a) core/blocking/markers.yaml 의 로그인·캡차·차단 마커에 매칭되거나, (b) http 401·403·429 이거나,
      (c) http 200 이면서 body 길이가 해당 소스 min_body_bytes 미만인 경우
    must_not: >
      계정 로그인, 세션 쿠키 주입, User-Agent 무작위화, 프록시/IP 로테이션, 헤드리스 탐지 우회 옵션으로
      재요청하거나, (c)를 정상 응답으로 간주해 success 처리
    because: >
      접근통제 회피는 정보통신망법상 침해 소지가 있고 D3 실사의 전제(비로그인 공개 정보)를 파기한다.
      또한 마커 사전에 없는 신종 차단 페이지는 200 + 빈 본문으로 오는 경우가 많아, 크기 하한이 없으면
      "차단당하는 중인데 정상 수집으로 집계"되는 상태가 며칠간 지속된다.
    detect: >
      테스트 test_blocked_access — 마커 픽스처·401/403/429·빈 본문(200) 각 케이스에서 status=blocked_access,
      아웃바운드 재요청 0회 assert + CI 금지 심볼 검사(stealth 계열 패키지, 프록시 로테이션 설정 키,
      랜덤 UA 라이브러리)가 core/ 의존성·코드에 존재하면 실패
    on_violation: block_merge

  - id: FORBID-5
    when: >
      blob 스토어 write가 예외로 실패했거나, 저장 후 재조회한 body의 sha256이 봉투의 body_sha256과
      불일치한 경우
    must_not:     "job을 status=success로 마킹하거나 후속 파이프라인 큐에 결과를 전달"
    because: >
      원문 없이 파생 레코드만 남으면 C4 파싱 규칙 개정 시 재처리 대상이 조용히 누락되고, 커버리지
      지표(H1)는 정상으로 보이는데 실제 데이터는 복구 불가능한 상태가 된다.
    detect: >
      통합테스트 test_storage_failure_not_success — write 실패·해시 변조 2개 시나리오에서
      job status ∈ {failed, dead_letter} 이고 다운스트림 큐 적재 0건 assert
    on_violation: block_merge

  - id: FORBID-6
    when: >
      원문(source_record 행 또는 blob 객체)에 대한 삭제·덮어쓰기 요청에 W8 파기 티켓 ID 또는
      법적 삭제 명령 문서 ID가 첨부되지 않은 경우
    must_not: >
      source_record 행 UPDATE/DELETE, blob 객체 삭제·덮어쓰기, 또는 `crawler.purge` 외 경로로 원문 제거.
      티켓이 있는 경우에도 삭제 범위는 blob 객체로 한정하며 DB 행과 감사 로그는 남긴다
    because: >
      원문 이력이 사라지면 "이 가격이 언제 어디서 왔는가"를 증명할 수 없어 정보 정정 요구(S5/W7)에
      대응할 근거가 사라진다. 반대로 무조건 보존으로 두면 body에 포함된 리뷰 작성자 개인정보의
      파기 요구에 응할 수 없어 규칙이 첫 요구 때 깨진다 — 그래서 파기 경로를 규칙 안에 지정 절차로 둔다.
    detect: >
      (a) `pytest -k test_purge_requires_ticket` — 티켓 ID 없이 crawler.purge 실행 시 non-zero exit,
      blob 삭제 0건, 감사 로그 append 0건 assert.
      (b) `pytest -k test_purge_keeps_row` — 티켓 있는 purge 후 source_record 행 수 불변,
      봉투의 blob_key 가 tombstone 상태로 조회되며 audit/purge/<date>.jsonl 에 1행 추가됨을 assert.
      (c) CI grep — core/ 내 source_record 대상 UPDATE/DELETE SQL·ORM 호출이 crawler.purge 모듈 밖에 존재하면 실패
      (DB 트리거는 F2 REQ-6이 이미 강제하므로 본 검사는 blob 경로와 우회 호출을 대상으로 한다).
    on_violation: block_merge
