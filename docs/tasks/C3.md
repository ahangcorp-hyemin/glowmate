## §A 분할 결정과 파생 규칙

### A-1. 왜 쪼개는가

| 신호 (02-spec §4) | C3 원안에서의 발현 |
|---|---|
| 되돌릴 때 일부만 되돌리고 싶어진다 | 원안 rollback이 이미 `adapters.<source_id>.enabled=false` 로 **소스 단위 분리**를 전제했다 |
| 리뷰어가 두 종류의 전문성을 요구받는다 | 소스마다 접근 방식(HTML 스크레이핑 / 공식 API / 시드 URL 순회)과 실패 모드가 다르다 |
| 계약 시점에 산출물 수가 확정되지 않는다 | D3 REQ-6의 어댑터 대상 목록은 1~5개 사이에서 D3 머지 시점에 확정된다 |

한 PR에 N개 어댑터를 묶으면 **한 소스의 셀렉터 문제로 전부 롤백**되고, 그 순간 이미 정상 동작하던 소스의 수집도 멈춘다.

> **2026-08-03 D3 확정 반영** — A-2 의 파생 모집단(`verdict ≠ forbidden`)을 현재 `verdicts.csv` 로 평가하면
> `official_website` **1건**뿐이다(`daangn`·`visitkorea` 는 `pending` 이라 모집단이 아니며, ToS 확보 시 재편입).
> `naver_place`·`kakao_map` 은 모집단에서 빠졌으므로 §B 는 보류(§0)이고, **파생 대상 = {`official_website`}** 이다.
> 즉 `C3x-ADAPTER-OFFICIAL_WEBSITE` 1건이 §C 템플릿으로 인스턴스화되어야 하나, 레지스트리 등재는 리드 승인 사항이며
> **본 개정에서는 신설하지 않는다**(§E 상신).

```

```

### A-3. 파생 태스크가 지켜야 할 불변 조건

1. **소스 1개 = 태스크 1개 = PR 1개.** 두 소스를 한 PR에 담지 않는다.
2. `touches` 는 `services/crawler/adapters/<source_id>/**` 와 그 테스트·픽스처 경로로 한정한다. 공용 파일(`core/**`, `pyproject.toml`)은 어떤 파생 태스크도 수정하지 않는다 — 등록은 C1의 규약 기반 자동 발견으로만 이루어진다.
3. §C 템플릿의 **REQ 8개·FORBID 6개를 모두 상속**하며, 임계값·표본 수만 소스 특성에 맞게 채운다. 항목을 삭제하려면 그 사유를 계약에 적고 리드 승인을 받는다.
4. **스텁 어댑터 금지**: 파생 태스크는 반드시 자기 소스의 수집 하한(REQ-2·REQ-4·REQ-8)을 갖는다. "등록만 되어 있고 아무것도 못 모으는 어댑터"가 계약을 통과하는 경로를 남기지 않는다.
5. 공통 로직이 필요해지면 그것은 **C1의 변경 요청**이며, 파생 태스크에서 구현하지 않는다.

## §C 파생 태스크 계약 템플릿 — `C3x-ADAPTER-<SOURCE_ID_UPPER>`

> D3 확정 목록의 **비할당 소스 1개당 1건**으로 인스턴스화한다. `<>` 표기는 인스턴스화 시 반드시 치환한다.
> 치환하지 않은 `<>` 가 남아 있으면 감사에서 자동 반려한다 (CI job `adapter-task-coverage` 가 placeholder 잔여를 검사).

### C-1. 소스별로 채워야 하는 파라미터

| 파라미터 | 채우는 근거 | 미기재 시 |
|---|---|---|
| `<SOURCE_ID>` | D3 verdicts.csv 의 source 값 | 반려 |
| `<HOST>` | D3 crawl_policy.yaml 의 대상 호스트 | 반려 |
| `<DISCOVERY_MODE>` | `keyword_search` / `seed_url_list` / `official_api` 중 1 (D3 access_method) | 반려 |
| `<REQUIRED_KEYS>` | 최소 name + source_url. 소스가 주소·카테고리를 제공하지 않으면 그 사실을 D3 실사표 참조로 명시 | 반려 |
| `<DEV_N> / <HOLDOUT_N>` | 모집단 규모에 따라. 홀드아웃은 최소 10건, 가격 라벨 케이스 최소 5건 | 반려 |

## §D 보류 중에도 살아 있는 범위 — 카카오 **장소 ID join key**

### D-1. 무엇이 허용되는가

D3 실사와 후속 API 실사에서 카카오 쪽 금지의 **유일한 명시 예외**로 확인된 것은 다음 하나다:

> **카카오 장소 ID(`place_url` 의 `<placeId>`)를 join key 로 저장하는 것**은 허용된다.

즉 다른 경로(`official_website` 등)로 이미 확보한 업체 레코드에 "이 업체는 카카오 place `<id>` 이다"라는
**식별자 한 개를 붙여 두는 보조 용도**는 살아 있다. 반면 아래는 §0 게이트가 닫힌 동안 전부 금지다(FORBID-1 (z)):

| 행위 | 가부 | 근거 |
|---|---|---|
| 장소 ID 를 join key 컬럼에 저장 | **허용** | 명시 예외 |
| 장소명·주소·카테고리·좌표·평점·리뷰 등 **필드 값** 저장 | 금지 | 운영정책 제5조 20·30항(결과 저장 금지) |
| 로컬 API 응답 원문(JSON) 스냅샷 보관 | 금지 | 동상 |
| `place.map.kakao.com/<id>` 를 fetch | 금지 | robots `Disallow: /` |
| 좌표 격자 분할로 45건 캡 우회해 전수 나열 | 금지 | 캡 우회 이전에 **목적(데이터셋 구축)이 금지** |

### D-2. 판단 — 이건 C3 본문이 아니라 **별도 소규모 계약**이 맞다

| 판단 근거 | 내용 |
|---|---|
| 목적이 다르다 | §B 는 "모집단 확보 + 가격 원문 수집"이다. join key 는 "이미 있는 레코드에 외부 식별자 부착"으로, H1·H2 가 아니라 C5 엔티티 해소·W7 정정 추적을 돕는 보조 기능이다 |
| 산출물이 다르다 | §B 산출물은 어댑터 3종 메서드·확장 스키마·픽스처 60건. join key 는 **컬럼 1개 + 부착 규칙 + 부착률 REQ** 뿐이다 |
| 게이트가 다르다 | §B 는 verdict 해금까지 착수 불가. join key 는 **지금 착수 가능**하다. 한 계약에 묶으면 살아 있는 범위가 죽은 범위에 인질로 잡힌다 |
| 롤백 단위가 다르다 | join key 부착은 컬럼 드롭으로 되돌아가고, 어댑터는 소스 비활성화로 되돌아간다 |
| 위험 프로필이 다르다 | join key 의 진짜 위험은 "ID 만 저장한다"는 경계가 슬금슬금 넓어져 이름·주소까지 캐시되는 것 — §B 의 FORBID 세트로는 이 위험을 겨냥하지 못한다 |

**제안(신설하지 않음, 리드 승인 사항):** `C3k-KAKAO-PLACE-ID-JOIN` — 규모상 REQ 3~4개·FORBID 3개 수준.
계약을 쓴다면 최소한 다음 금지를 포함해야 한다는 점만 기록해 둔다(본 개정에서 계약 파일은 만들지 않았다):

- 카카오 응답에서 `id` 이외 필드를 영속 저장소에 기록할 때 → 차단 (스키마 컬럼 화이트리스트 + CI 대조)
- 장소 ID 를 키로 상세 페이지를 fetch 하려 할 때 → 차단 (host allowlist 에 kakao 미등재 유지)
- join key 부착률을 높이려 이름·주소 문자열을 카카오에서 역조회해 캐시할 때 → 차단

### D-3. 이 절이 §B 를 열어 주지 않는다

§D 는 **§0 조건식과 무관**하다. join key 예외를 근거로 §B 를 부분 착수하거나, `verdicts.csv` 의
`kakao_map` verdict 를 `conditional` 로 바꾸는 근거로 삼는 것은 FORBID-6 위반이다.
