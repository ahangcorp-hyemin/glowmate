>
> ⚠️ §C의 파생 태스크 ID는 아직 `03-task-dag.md` 정본 레지스트리에 없다. **레지스트리 등재는 팀 리드 승인 사항**이며,
> 승인 전에는 어떤 파생 태스크도 착수하지 않는다. 본 문서는 규칙과 템플릿만 제공한다.

## §A 분할 결정과 파생 규칙

### A-1. 왜 쪼개는가

| 신호 (02-spec §4) | C3 원안에서의 발현 |
|---|---|
| 되돌릴 때 일부만 되돌리고 싶어진다 | 원안 rollback이 이미 `adapters.<source_id>.enabled=false` 로 **소스 단위 분리**를 전제했다 |
| 리뷰어가 두 종류의 전문성을 요구받는다 | 소스마다 접근 방식(HTML 스크레이핑 / 공식 API / 시드 URL 순회)과 실패 모드가 다르다 |
| 계약 시점에 산출물 수가 확정되지 않는다 | D3 REQ-6의 어댑터 대상 목록은 1~5개 사이에서 D3 머지 시점에 확정된다 |

한 PR에 N개 어댑터를 묶으면 **한 소스의 셀렉터 문제로 전부 롤백**되고, 그 순간 이미 정상 동작하던 소스의 수집도 멈춘다.

### A-2. 파생 규칙 (기계 적용 가능)

```
파생 모집단  = docs/discovery/D3/report.md 의 "어댑터 대상 소스 확정 목록"
             (= verdicts.csv 에서 verdict ≠ forbidden 인 소스 집합, D3 REQ-6이 양자 일치를 강제)
이미 할당됨  = naver_place → C2-ADAPTER-NAVER
             = kakao_map   → C3-ADAPTER-KAKAO (§B)
파생 대상    = 파생 모집단 − {naver_place, kakao_map}
생성 규칙    = 파생 대상 소스 1개당 태스크 1개, §C 템플릿을 인스턴스화
ID 명명(제안) = C3b-ADAPTER-<SOURCE_ID_UPPER>, C3c-…  (source_id 사전순으로 b, c, d…)
파생 시점    = D3 머지 + G3 판정 통과 직후, 착수 전
검증         = CI job `adapter-task-coverage` — 파생 모집단의 각 source_id 에 대해
              docs/tasks/ 아래 계약 파일이 1:1로 존재하지 않으면 exit 1
              ⚠️ 이 잡은 코드가 아니라 **계약 문서**를 검사하므로 소유 태스크가 아직 없다.
              배치 제안: O3-DEPLOY-MONITORING 또는 리드 운영 스크립트. 리드 승인 전까지는
              리드가 D3 머지 시점에 수동 대조한다 (자동화 불가가 아니라 소유자 미지정이다)
```

### A-3. 파생 태스크가 지켜야 할 불변 조건

1. **소스 1개 = 태스크 1개 = PR 1개.** 두 소스를 한 PR에 담지 않는다.
2. `touches` 는 `services/crawler/adapters/<source_id>/**` 와 그 테스트·픽스처 경로로 한정한다. 공용 파일(`core/**`, `pyproject.toml`)은 어떤 파생 태스크도 수정하지 않는다 — 등록은 C1의 규약 기반 자동 발견으로만 이루어진다.
3. §C 템플릿의 **REQ 8개·FORBID 6개를 모두 상속**하며, 임계값·표본 수만 소스 특성에 맞게 채운다. 항목을 삭제하려면 그 사유를 계약에 적고 리드 승인을 받는다.
4. **스텁 어댑터 금지**: 파생 태스크는 반드시 자기 소스의 수집 하한(REQ-2·REQ-4·REQ-8)을 갖는다. "등록만 되어 있고 아무것도 못 모으는 어댑터"가 계약을 통과하는 경로를 남기지 않는다.
5. 공통 로직이 필요해지면 그것은 **C1의 변경 요청**이며, 파생 태스크에서 구현하지 않는다.

forbid:

    when: >

      차단을 5xx·빈 200으로 위장해 반환하는 경우가 있어, 이 신호를 정상으로 삼키면 수집량이 0으로 떨어진
      상태가 며칠간 초록불로 유지되고 C5의 교차 검증이 소리 없이 사라진다.

      stealth 계열 의존성·core.fetcher 외 네트워크 심볼 import 가 있으면 실패

    detect: >
      테스트 kakao_empty_not_success — discover 0건·손상 픽스처 6건·가격 라벨 결측 픽스처 4건에서

    detect: >
      테스트 kakao_price_verbatim — price_raw[*] 각 값이 원본 body의 substring인지 assert

    when:         "리뷰·후기 영역 또는 업체 소개 본문에서 필드를 추출할 때"

      스냅샷까지 남기므로 위반 규모가 크롤 회차만큼 누적된다.
    detect: >
      테스트 kakao_pii_scan(정규식 + 확장 스키마 additionalProperties=false) — PII 픽스처 12건 검출 0건 assert +

    when: >
      PR diff가 dataset_manifest.json · manifest.lock · 홀드아웃 픽스처 · 라벨 파일 · 필수 키 목록 ·

      난이도 조절로 언제든 충족되어 품질 REQ 전체가 장식이 된다.
    detect:       "CI job `dataset-lock` — 해당 경로 diff 감지 시 라벨 부재면 exit 1, manifest.lock 재계산 불일치면 exit 1"

## §C 파생 태스크 계약 템플릿 — `C3x-ADAPTER-<SOURCE_ID_UPPER>`

> D3 확정 목록의 **비할당 소스 1개당 1건**으로 인스턴스화한다. `<>` 표기는 인스턴스화 시 반드시 치환한다.
> 치환하지 않은 `<>` 가 남아 있으면 감사에서 자동 반려한다 (CI job `adapter-task-coverage` 가 placeholder 잔여를 검사).

### C-1. 소스별로 채워야 하는 파라미터

| 파라미터 | 채우는 근거 | 미기재 시 |
|---|---|---|
| `<SOURCE_ID>` | D3 verdicts.csv 의 source 값 | 반려 |
| `<HOST>` | D3 crawl_policy.yaml 의 대상 호스트 | 반려 |
| `<DISCOVERY_MODE>` | `keyword_search` / `seed_url_list` / `official_api` 중 1 (D3 access_method) | 반려 |
| `<REQUIRED_KEYS>` | 최소 name + source_url. 소스가 주소·카테고리를 제공하지 않으면 그 사실을 D3 실사표 참조로 명시 | 반려 |
| `<DEV_N> / <HOLDOUT_N>` | 모집단 규모에 따라. 홀드아웃은 최소 10건, 가격 라벨 케이스 최소 5건 | 반려 |
| `<PRICE_RECALL>` | 기본 0.85. 하향하려면 소스 특성 근거 + 리드 승인 | 기본값 적용 |
| `<SMOKE_N>` | 실수집 스모크 건수, 최소 10 | 반려 |
