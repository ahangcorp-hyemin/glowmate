# Task Contract Spec — 태스크 계약 작성 규격

> 이 문서는 glowmate의 모든 개발 태스크가 따라야 하는 **작성 규격**이다.
> 규격을 위반한 태스크는 `task-auditor` 에이전트가 **반려(REJECT)** 하며, 반려된 태스크는 개발 에이전트에게 전달되지 않는다.

---

## 0. 근본 원칙

### 원칙 1 — 태스크 1개 = PR 1개 = 에이전트 1개
하나의 태스크는 **되돌릴 수 있는 단일 변경 단위**여야 한다. 두 개의 관심사가 섞이면 롤백이 불가능해지고, 리뷰가 불가능해지고, 병렬화가 불가능해진다.

### 원칙 2 — 금지사항은 **반드시 조건부**로 쓴다
> **무조건 금지는 반드시 깨진다. 한 번 깨지면 규칙 전체가 무시된다.**

`"절대 any 를 쓰지 마라"` 같은 무조건 금지는 현실의 예외 앞에서 무너지고, 그 순간 개발자(또는 에이전트)는 **다른 모든 금지사항도 협상 가능한 것으로 학습한다.** 그래서 금지사항은 예외를 규칙 **안으로** 끌고 들어와야 한다:

```
WHEN <판정 가능한 조건> → MUST NOT <행위>
```

조건이 없으면 그건 금지사항이 아니라 **잔소리**다.

### 원칙 2.5 — 모든 금지는 짝이 되는 **정상 동작 요구**를 가진다

> **금지만 쌓으면, 아무것도 하지 않는 구현이 만점을 받는다.**

`PriceDisplay` 가 항상 "미공개"를 렌더하면 "잘못된 가격을 노출하지 마라"는 전부 준수된다. medical 가격을 전부 숨기면 의료광고법 FORBID가 전부 준수된다. 필터 태그를 하나도 안 붙이면 태그 오류가 0건이다.

**규제·신뢰 리스크에 대한 방어는 제품 기능을 0으로 만드는 방향으로 항상 열려 있다.** 그래서 무언가를 숨기거나 거르거나 차단하는 FORBID를 쓸 때는, 반드시 **최소 정상 동작 커버리지 REQ**를 짝으로 둔다:

```yaml
forbid:
  - id: FORBID-2
    when:     신뢰도 스코어가 임계 미만인 경우
    must_not: 가격을 확정값으로 렌더

requirements:
  - id: REQ-5      # ← FORBID-2의 짝. 없으면 반려
    statement: 고신뢰 입력 골든 40건 중 숫자 가격이 실제로 렌더되는 비율 100%
    acceptance: "`pnpm test:price-display` — 전량 미공개 렌더 시 실패"
```

**검사 방법:** 각 FORBID에 대해 *"이 금지를 극단적으로 준수하면 제품이 사라지는가?"* 를 묻는다. 사라진다면 짝이 되는 positive REQ가 없는 것이다.

### 원칙 3 — 탐지할 수 없는 금지는 금지가 아니다
모든 `FORBID` 항목은 `DETECT`(어떻게 위반을 잡아내는가)를 가져야 한다. 사람 눈으로만 잡히는 규칙은 3주 뒤에 반드시 뚫린다. 우선순위: **자동 테스트 > CI 체크 > 린트 규칙 > 리뷰 체크리스트**.

### 원칙 4 — 주관적 형용사 금지
`빠르게` `적절히` `사용자 친화적으로` `깔끔하게` `안정적으로` 는 요구사항이 아니다. 측정치와 임계값으로 바꾼다.

## 1. 계약 포맷

```yaml
# ─── 식별 ───────────────────────────────
id:            C4-PRICE-NORMALIZER        # {Phase}{번호}-{SLUG}
title:         가격 정규화 엔진 (회당 단가 환산)
workstream:    pipeline                    # discovery | foundation | pipeline | web | ops
owner_agent:   dev-pipeline                # 이 태스크를 수행할 에이전트 타입

# ─── 존재 이유 ──────────────────────────
traces_to:     [H2, S1, KM-price-coverage] # PRD 가설/솔루션/지표 참조 (필수, 1개 이상)
why:           "1문장. 이게 없으면 무엇이 불가능해지는가."

# ─── DAG ────────────────────────────────
depends_on:    [F2-SCHEMA, C1-CRAWLER-CORE]
blocks:        [W3-VENUE-DETAIL, C7-QUALITY-GATE]
parallel_with: [C5-ENTITY-RESOLUTION, C6-TAG-ASSIGN]
gate:          G1                          # 이 게이트 통과 전 착수 금지 (없으면 null)

# ─── 산출물 ─────────────────────────────
deliverable:
  pr_count:    1
  touches:     [packages/pipeline/src/price/**]   # 이 경로 밖은 건드리지 않음
  artifacts:   ["price 정규화 모듈", "단위테스트", "실패 사유 코드 표"]

# ─── 요구사항 ───────────────────────────
requirements:
  - id: REQ-1
    statement: <관측 가능한 서술>
    acceptance: <기계 검증 가능한 확인 방법>

# ─── 조건부 금지사항 ────────────────────
forbid:
  - id: FORBID-1
    when:         <판정 가능한 조건>
    must_not:     <금지 행위>
    because:      <이 금지가 없으면 발생하는 구체적 실패>
    detect:       <위반 탐지 수단>
    on_violation: block_merge | rollback | alert

# ─── 경계 ───────────────────────────────
out_of_scope:  [<이 태스크에서 명시적으로 하지 않는 것>]
rollback:      <되돌리는 방법>
done_when:     [<Definition of Done 체크리스트>]
```

## 2. `requirements` 작성 규칙

| 규칙 | 내용 |
|---|---|
| R-1 | 각 REQ는 **주어 + 동사 + 측정치** 형태. 측정치가 없으면 반려 |
| R-2 | 각 REQ는 대응하는 `acceptance` 를 **정확히 1개 이상** 가진다 |
| R-3 | `acceptance` 는 **기계가 판정 가능**해야 한다 (테스트 명령, CI 잡, 쿼리 결과) |
| R-4 | 하나의 REQ에 `그리고`로 두 가지 요구를 묶지 않는다 → 분리 |
| R-5 | 금지 어휘: `빠르게` `적절히` `사용자 친화적` `깔끔하게` `안정적으로` `최적화` `개선` |
| **R-6** | **평가 데이터의 표집 절차를 REQ에 명시하고, 홀드아웃을 분리한다** (아래 §2.1) |
| **R-7** | **픽스처만으로 충족 가능한 REQ만 있으면 안 된다. 실데이터/실환경 하한 REQ를 최소 1개 둔다** (아래 §2.2) |

### 2.1 자기 출제·자기 채점 금지 (R-6)

품질 임계(`정확도 ≥ N%`, `재현율 ≥ N%`)를 REQ로 두면서 그 평가 데이터를 **구현자가 직접 만들면**, 임계는 난이도 조절로 언제든 충족된다. 여기에 "픽스처 동결" FORBID를 붙이면 **쉬운 시험지를 봉인**하는 결과가 된다.

품질 임계 REQ가 있는 태스크는 반드시:

- **표집 절차를 REQ에 명시** — 모집단, 추출 방법, 층화 기준. "대표적인 200건"은 절차가 아니다
- **홀드아웃 분리** — 개발 중 열람 불가한 평가셋을 별도로 두고, 최종 판정은 홀드아웃에서 낸다
- 정답 라벨을 구현자가 만든 경우 **그 사실과 검증 방법을 명시**

### 2.2 픽스처 세계 탈출 (R-7)

모든 REQ가 픽스처 위에서만 판정되면, **아무것도 하지 않는 구현이 전 CI를 녹색으로 통과**한다. 수집 0건, 추출 0건, 산출 0건이 전부 합법이 된다.

외부 데이터·네트워크·실환경을 다루는 태스크는 **실환경 하한 REQ**를 최소 1개 둔다:

```
✗ REQ: 골든 픽스처 200건에서 파싱 성공률 ≥ 80%
✓ REQ: 위 + 실제 수집 데이터 표본에서 회당 단가 산출 건수 ≥ N건 (스모크)
```

**나쁜 예 → 좋은 예**

```
✗ REQ-1: 가격 파싱이 안정적으로 동작해야 한다
✓ REQ-1: 골든 데이터셋 200건에 대해 회당 단가 파싱 성공률 ≥ 80%
   acceptance: `pnpm test:price-golden` 통과 (임계값 하드코딩)
```

## 3. `forbid` 작성 규칙 — 가장 중요

### 3.1 5요소 전부 필수

| 요소 | 질문 | 누락 시 |
|---|---|---|
| `when` | **언제** 이 금지가 발동하는가 | 반려 — 무조건 금지는 금지사항이 아님 |
| `must_not` | 무엇을 하면 안 되는가 | 반려 |
| `because` | 어기면 **어떤 구체적 실패**가 나는가 | 반려 — 이유 없는 규칙은 무시됨 |
| `detect` | **어떻게** 잡아내는가 | 반려 — 탐지 불가 규칙은 장식 |
| `on_violation` | 잡으면 어떻게 하는가 | 반려 |

### 3.2 `when` 조건이 갖춰야 할 성질

- **판정 가능**: 사람마다 다르게 읽히면 안 된다
- **관측 가능**: 코드/CI/런타임에서 확인 가능해야 한다
- **좁다**: 조건이 넓을수록 무조건 금지에 가까워지고, 그만큼 잘 깨진다

```
✗ when: "데이터가 부실할 때"                    ← 판정 불가
✓ when: "원문 문자열에서 (총액·횟수·유효기간) 중 1개 이상 파싱 실패한 경우"
```

### 3.3 실제 예시 — C4 가격 정규화 엔진

```yaml
forbid:
  - id: FORBID-1
    when:     원문 가격 문자열에서 (총액, 횟수, 유효기간) 중 하나라도 파싱에 실패한 경우
    must_not: 나머지 값으로 회당 단가를 추정해 price_per_session 필드에 기록
    because:  추정 가격이 확정 가격과 구분 없이 노출되면, UVP 전체가 걸려 있는
              "가격 신뢰"가 단 한 건의 오차로 붕괴한다
    detect:   단위테스트 — 결손 입력 12개 케이스 각각에 대해 반드시
              null + failure_reason 코드를 반환하는지 검증
    on_violation: block_merge

  - id: FORBID-2
    when:     동일 업체에 대해 서로 다른 소스에서 회당 단가가 30% 이상 차이나는 경우
    must_not: 임의의 한쪽을 대표값으로 선택해 단독 노출
    because:  근거 없는 선택은 "가격이 틀린 사이트"라는 평판을 만들고,
              한 번 생긴 평판은 데이터를 고쳐도 회복되지 않는다
    detect:   통합테스트 — 충돌 픽스처 입력 시 conflict 플래그와
              양쪽 값이 모두 보존되는지 검증
    on_violation: block_merge

  - id: FORBID-3
    when:     카테고리가 medical_wellness 인 경우
    must_not: 가격을 시술명과 직접 결합한 형태로 공개 필드에 노출
    because:  의료광고법상 비급여 진료비의 비교·유인 표시는 규제 대상이며,
              위반 시 서비스 전체가 중단될 수 있다
    detect:   CI 스키마 체크 — medical_wellness 레코드의 public_price_display
              가 허용 포맷 화이트리스트에 속하는지 검사
    on_violation: block_merge
```

### 3.4 안티패턴

| 안티패턴 | 왜 나쁜가 |
|---|---|
| `must_not: 하드코딩하지 말 것` | 조건도 탐지도 없음. 잔소리 |
| `when: 항상` | 조건부가 아님. 원칙 2 위반 |
| `detect: 코드리뷰에서 확인` | 3주 뒤 뚫림. 최후수단으로만 허용하며 이때 사유를 명시 |
| `because: 좋은 관행이므로` | 실패 시나리오가 없음. 규칙이 협상 대상이 됨 |
| 금지사항 12개 나열 | 전부 무시된다. **태스크당 3~6개**, 진짜 위험한 것만 |
| 숨김·차단 FORBID에 짝이 되는 positive REQ 없음 | 아무것도 안 하는 구현이 만점. 원칙 2.5 위반 |
| 사후 완화만 막고 **사전 설정은 무방비** | 임계·정의·상한을 원하는 결론이 나오게 미리 정한 뒤 잠그면 100% 준수. **잠금 대상의 허용 범위를 계약 본문에 못박아라** |
| 계약이 **자기 PR을 차단** (최초 도입 파일이 자기 FORBID에 걸림) | 개발 에이전트가 반드시 우회하며, 우회 관용구를 학습한다. 예외를 규칙 안으로 명시하라 |
| `on_violation: block_merge` 인데 **집행할 CI job이 없음** | 원칙 3 위반. CI 소유 태스크를 `depends_on` 에 넣거나 detect를 하향 조정 |

## 4. 태스크 분할 규칙 (PR 1개 원칙)

**분할해야 하는 신호**

- `touches` 경로가 서로 다른 workstream을 넘나든다
- 되돌릴 때 일부만 되돌리고 싶어진다
- 리뷰어가 두 종류의 전문성을 요구받는다
- `requirements` 가 8개를 넘는다

**분할하면 안 되는 신호 (억지 분할 금지)**

- 쪼개면 중간 상태가 **동작하지 않는다** → 하나로 둔다
- 쪼갠 두 PR이 항상 같이 머지되어야 한다 → 하나로 둔다

## 5. 감사 판정

`task-auditor` 는 각 태스크에 대해 아래 중 하나를 낸다:

| 판정 | 의미 |
|---|---|
| `PASS` | 개발 에이전트에게 전달 가능 |
| `REVISE` | 결함이 있으나 저자가 수정 가능. **결함마다 구체적 지적 필수** |
| `REJECT` | 태스크 자체가 잘못 정의됨 (범위 초과, DAG 모순, 존재 이유 없음) |

### 반려 사유 체크리스트

```
[구조]
□ traces_to 가 비었거나 PRD에 없는 ID를 참조
□ depends_on 에 순환 의존 존재
□ depends_on 이 DAG에 존재하지 않는 태스크를 참조
□ gate 를 무시하고 게이트 이후 작업을 선행 배치
□ 하나의 태스크가 2개 이상 PR로 나뉘어야 함 (관심사 혼합)

[요구사항]
□ 주관적 형용사 사용
□ acceptance 가 없거나 기계 검증 불가
□ REQ 하나에 복수 요구가 '그리고'로 결합
□ requirements 가 8개 초과

[금지사항]
□ forbid 항목이 0개  ← 위험이 없는 태스크는 없다
□ when 이 없거나 '항상'에 해당
□ detect 가 없음
□ because 에 구체적 실패 시나리오가 없음
□ detect 가 전부 '코드리뷰'  ← 자동화 가능한데 미룬 것
□ forbid 가 7개 이상 (실효성 상실)
□ 품질 임계 REQ가 있는데 표집 절차·홀드아웃 규정이 없음 (R-6)
□ 전 REQ가 픽스처만으로 충족 가능 — 실환경 하한 부재 (R-7)
□ detect 가 참조하는 테이블/컬럼/함수가 선행 태스크 산출물에 실재하지 않음
   ← 대상 부재 시 grep 기반 detect 는 위반해도 공허하게 통과한다

[경계]
□ out_of_scope 미정의
□ touches 경로 미정의 또는 과도하게 넓음 (예: src/**)
□ rollback 미정의
```

> **감사는 적대적으로 수행한다.** "괜찮아 보인다"는 판정이 아니다. 결함을 찾지 못했다면 **어떤 공격을 시도했는지** 명시해야 PASS로 인정된다.
