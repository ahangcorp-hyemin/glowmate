## W1-SEO-FOUNDATION — REVISE

### 규격 위반
- `[구조] depends_on 이 DAG에 존재하지 않는 태스크를 참조` — `depends_on: [F2, F3]`. `03-task-dag.md` L13은 **`F3-DESIGN-TOKENS ← 폐기(DS 워크스트림으로 대체). 신규 참조 금지`** 를 명시한다. 대체 노드는 DS1(토큰)·DS3(shadcn 초기화)·DS5(코어 컴포넌트)·DS6(a11y CI 게이트)다.
- `[구조] depends_on/blocks 가 ID 정본과 불일치` — 정본 레지스트리는 `W1-SEO-FOUNDATION`·`F2-SCHEMA` 같은 완전 문자열을 요구한다(`03-task-dag.md` L5). 본 계약은 `F2`,`F3`,`W2`… 축약형을 쓴다. C 배치는 완전형(오타 포함)을 썼다 → **두 배치가 서로 다른 표기 규약을 쓰므로 DAG 자동 검증이 어느 쪽으로도 성립하지 않는다.**
- `[구조] gate 를 무시하고 게이트 이후 작업을 선행 배치` — `gate: null`. W1은 Phase 3이고 PRD §4는 "G1·G2·G3 통과 전 Phase 2 이후 태스크 착수 금지"다. 같은 배치의 W5·W6·W7은 `[G1,G2,G3]` 를 선언했다. 동일 Phase 안에서 게이트 선언이 두 갈래다.
- `[구조] traces_to 가 PRD에 없는 ID를 참조` — `KM-search-to-detail-ctr`. lean canvas §7 표에 "검색 → 상세 CTR ≥ 15%" 라는 **문장**은 있으나 `KM-*` 라는 ID 네임스페이스는 어느 문서에도 정의되지 않는다. O1 REQ-3이 "문서 표를 파싱해 상수와 비교"하는 CI를 만들 예정이므로 이 부재는 실제로 CI를 깨뜨린다.
- `[금지사항] detect 가 참조하는 대상이 선행 태스크 산출물에 실재하지 않음` — REQ-8·FORBID-2의 검증 대상인 `is_public` 은 **F2 산출물에 없다.** F2 REQ-5가 정의한 것은 `venue.visibility ENUM('public','hidden_quality','hidden_request','hidden_legal')` 이며, C7은 out_of_scope에서 컬럼 추가를 금지하고 DDL을 `public_venue` 뷰 1개로 한정한다. **`is_public` 컬럼을 만드는 태스크가 전 계획에 존재하지 않는다.**
- `[경계] touches 과도` — `.github/workflows/ci.yml` 전체를 열어두고 "잡 추가만"이라는 주석 제약만 있다. 기계 검증 수단이 없다.

### 공격 결과
- **A 악의적 준수** — 세 갈래 시도.
  1. **`revalidate` 상한 부재.** REQ-6은 `export const revalidate = <숫자>` 선언만 요구하고 값의 상한이 없다. `revalidate = 31536000`(1년)을 선언하면 REQ-6·FORBID-1을 100% 준수하면서 C7이 비공개로 돌린 업체, W7 takedown이 수용된 업체가 1년간 정적 캐시로 계속 서빙된다. **더 근본적으로, 재검증 무효화 경로(`revalidatePath`/`revalidateTag`)를 소유한 태스크가 W1~O3 어디에도 없다.** C7 판정 결과가 웹에 도달하는 메커니즘이 계약상 존재하지 않는다 → **G4 우회 경로(신규).**
  2. **allowlist 무제한.** REQ-1 acceptance는 "스크립트 내 allowlist 파일에 명시된 3개 정적 경로만" 예외로 하는데, allowlist 파일 자체의 변경을 막는 수단이 없다. 3개를 300개로 늘려도 CI는 녹색이고 FORBID-5도 함께 무력화된다.
  3. **매니페스트 축소.** REQ-6·FORBID-1의 검사 범위는 "색인 대상 라우트 매니페스트"다. 매니페스트에서 라우트를 빼면 검사 대상에서 사라진다. 매니페스트를 잠그는 규정이 없다.
- **B 조건 회피** — FORBID-2의 `when` 은 "sitemap 생성기 또는 라우트 핸들러"로 한정된다. **빌드타임 정적 생성기(`generateStaticParams`)와 RSC 서버 컴포넌트는 이 문구에 걸리지 않는다.** W4 FORBID-4가 우연히 그 구멍을 메우지만 W1 레벨에서는 열려 있다. FORBID-3은 `lib/seo/**` 만 린트 대상이므로 `lib/routes/**` 에서 `headers()` 로 오리진을 만들면 회피된다(경로 빌더가 절대 URL을 만드는 것은 자연스러운 구현이다).
- **C 탐지 무력화** — FORBID-1의 detect는 "대표 라우트 4종 HTML을 fetch"인데 W1 `touches` 에 리스트·상세·조합 랜딩 라우트가 없다. REQ-8도 "is_public=false 픽스처 3건 404"를 요구하지만 검증할 라우트가 없다. **`fixtures/seo/**` 안에 통과용 더미 라우트를 만드는 것 외에 이 테스트를 CI에서 녹색으로 만들 방법이 없다.** 착수 시점부터 탐지가 허구다.
- **D 지름길 유도** — allowlist 확장, revalidate 극대화, 매니페스트 축소(위). 추가로 FORBID-4를 그대로 켜면 W2·W3가 물리적으로 구현 불가하므로(아래 E) 개발 에이전트는 **반드시 `app/api/**` 예외를 판다.** 예외를 파는 순간 "웹 컴포넌트의 DB 직접 호출 금지"라는 규칙 전체가 협상 가능한 것으로 학습된다(원칙 2의 붕괴 시나리오 그대로).
- **E DAG 정합성** — F3 폐기(위). `blocks: [W2,W3,W4,W5,W7]` 는 각 태스크 `depends_on` 과 상호 일치, 순환 없음 ✓. **FORBID-4가 PRD §2와 충돌한다:** PRD는 "Route Handler 기반 공용 API 레이어를 웹과 분리 / 웹 컴포넌트가 DB를 직접 호출하지 못하게 경계를 강제"를 요구하는데, FORBID-4의 `when` 은 `apps/web/src/app/**` 전체이고 W2·W3의 API 핸들러는 `apps/web/src/app/api/venues/route.ts` 에 놓인다. **API 레이어를 소유하는 태스크(`packages/api` 류)가 배치 전체에 존재하지 않는다.**
- **F 존재 이유** — H3 추적은 타당하다(URL 규약·sitemap·렌더링 전략이 없으면 롱테일 색인 자체가 불가). `KM-search-to-detail-ctr` 는 미정의 ID.

### 공격 결과
- **A 악의적 준수** — **`confidence` 캘리브레이션 부재가 FORBID-2를 통째로 공허하게 만든다.** W2의 4상태 판정은 `price_plan.confidence < 0.7` 을 estimated의 유일한 근거로 삼는데, C4 계약에도 W2 계약에도 **confidence 값의 산출 규칙이나 분포 제약이 없다.** C4가 전 레코드에 `confidence = 1.0` 을 부여하면 estimated 상태는 실데이터에서 영원히 발생하지 않고, W2 FORBID-2·REQ-4의 테스트는 손으로 만든 위반 픽스처에서만 참이 된다. **저신뢰 가격이 확정 가격으로 화면에 도달하는 경로가 열려 있다** → 결함.
  둘째 갈래: REQ-1은 "상위 20개 카드의 업체명 20건 + 가격 표기 20건"을 요구하는데 `가격 표기`에 **'가격 미공개' 문구가 허용**된다. 20건 전부 '가격 미공개'인 리스트가 REQ-1을 100% 충족한다. UVP(회당 단가 비교)를 한 건도 제공하지 않는 리스트가 합법이다.
- **B 조건 회피** — FORBID-6의 `when` 은 "카드의 **카테고리**가 medical_wellness". **F2 스키마에 category/category_axis 컬럼이 정의되어 있지 않고**, 이 축을 판정하는 정본은 D4 `medical_scope.yaml` 의 업종 enum인데 W2는 D4를 참조하지 않는다. 도수치료 업체가 C5·C6 단계에서 `운동·바디` 로 분류되면 FORBID-6의 `when` 이 발동하지 않고 의료광고 규제 표기가 **노출량이 가장 많은 표면**에 그대로 나간다.
  FORBID-3은 방어됨: `when`("0건 또는 3건 미만")이 좁지만 REQ-6이 완화 제안을 별도 섹션으로 분리했고 detect가 속성 테스트 100회라 우회가 어렵다. 이 배치에서 가장 잘 쓰인 조항 중 하나다.
- **C 탐지 무력화** — FORBID-1 detect의 "핸들러 소스에 원본 테이블명 grep 0건"은 C1-C7 감사 P3와 동일한 실패를 반복한다: ORM 사용 시 `prisma.venue`/`db.query.venue` 형태라 테이블명 문자열이 소스에 등장하지 않는다. 게다가 **C7이 아직 없는 상태에서 픽스처로 개발하면 grep 결과는 자동으로 0건**이므로 이 detect는 위반 여부와 무관하게 항상 통과한다.

1. **REQ-4에 "각 룰이 참조하는 메트릭이 실제 노출 엔드포인트에 존재함"을 검사하는 acceptance 추가 + 합성 발화 리허설 REQ 신설** — 예: "4개 룰 각각에 대해 조건을 인위적으로 충족시켜 채널에 실제로 전송되는 것을 스테이징에서 확인". 현행 스키마 검증만으로는 알림이 장식이다.
2. **W6·W7 의존 룰 2종을 별도 REQ로 분리하고 `depends_on` 또는 후속 배포 단계에 배치** — B2 착수 시점에 존재하지 않는 메트릭을 참조하는 현 구조는 반드시 공허해진다.
3. **FORBID-3의 `when` 에 "억제 창(suppression window) 연장"과 "룰 비활성화 플래그 설정"을 추가** — 현행 조건은 무음화 경로 3개 중 1개만 막는다.
4. **REQ-5의 억제 정책을 상태형/이벤트형 알림으로 분리** — 지속 상태 알림에 30분 재발화를 적용하면 노이즈 압력으로 규칙이 반드시 깨진다(원칙 2).
5. **Search Console·네이버 서치어드바이저 연동의 소유를 확정** — W1이 O3로 넘겼는데 O3에 없다. O1의 CTR 지표가 여기에 달려 있다.
6. `parallel_with` 의 F3 제거, ID 정본 표기로 교체.
7. drain 대기·롤백 소요 상수의 하향 금지 조항 추가.

## 종합 — 체계적 결함 패턴

### P1. `is_public` 이라는 유령 컬럼 (10건 중 7건이 의존)
**W1 REQ-8·FORBID-2 / W2 FORBID-1 / W4 FORBID-2·4 / W5 REQ-6·FORBID-4 / W7 FORBID-1 / O1 / O2 REQ-1·4·FORBID-1** 이 전부 `is_public` 위에 요구사항과 탐지를 세웠다. 그러나 F2가 정의한 것은 `venue.visibility ENUM('public','hidden_quality','hidden_request','hidden_legal')` 이고, C7은 out_of_scope에서 컬럼 추가를 금지하며 DDL을 `public_venue` 뷰 1개로 한정한다. **`is_public` 컬럼을 만드는 태스크가 계획 전체에 없다.**
단순한 명칭 불일치가 아니다:
- **비공개 사유가 3종에서 1종(boolean)으로 붕괴한다.** `hidden_request`(W7 삭제 요청)·`hidden_legal` 과 `hidden_quality` 를 구분할 수 없게 되고, 그래서 **O2가 삭제 요청 레코드를 되살릴 수 있고 W5가 삭제 요청 업체의 리포트를 계속 노출한다.**
- **grep/픽스처 기반 detect가 대상 부재로 공허하게 통과한다**(개정 §5 신규 항목에 정확히 해당).
→ **전달 전 조치: F2 `visibility` ENUM을 정본으로 확정하고 7개 계약의 참조를 일괄 정합화. 비공개 사유별 취급 규정을 각 계약에 명시.**

### P2. 픽스처 세계 탈출 실패 (R-7) — 10건 중 9건
O3를 제외한 전 계약이 픽스처·골든 데이터 위에서만 판정된다. 그 결과 **아무것도 산출하지 않는 구현이 전 CI를 녹색으로 통과한다:**

| 태스크 | 0-산출 합법 상태 |
|---|---|
| W2 | 리스트 0건 / 20건 전부 '가격 미공개' |
| W3 | 요금제 0건 상세만 존재 |
| W4 | **조합 페이지 0개 생성** (REQ-5는 generated+excluded 합계만 검사) |
| W5 | 리포트 0건 + sitemap 미등재 |
| W6 | 실트래픽 이벤트 0건 |
| O1 | **5개 카드 전부 unavailable** |

C1-C7 감사의 P1과 동일한 패턴이며, **파이프라인과 웹이 양쪽 다 0-산출 상태로 전 CI 녹색인 채 G1·G4 판정이 내려질 수 있다.**

### P3. C7 게이트 우회 — 신규 3경로 (기존 6건에 추가)
1. **W3 상세 API에 공개 판정 조항이 0건** — 리스트(W2)는 막혀 있는데 색인 가치가 더 높은 상세는 무방비.
2. **ISR/정적 캐시 무효화 경로의 소유자 부재** — W1 REQ-6은 `revalidate` 값에 상한이 없고, C7 판정 변경 시 웹을 무효화하는 메커니즘이 계약 전체에 없다. **G4는 빌드 시점에만 존재하는 게이트가 된다.**
3. **O2의 수동 override가 `confidence` 를 지정할 수 있어 2인 승인 조건 자체를 회피** — 스코어를 임계 위로 올리면 FORBID-1의 `when` 이 발동하지 않는다.

**공통 근원:** 저신뢰·충돌·미확정 데이터를 걸러내는 판정이 전부 `confidence` 와 `is_public` 이라는 **두 개의 파생 값**에 의존하는데, 그 두 값을 누가 어떤 규칙으로 만드는지가 계약 어디에도 고정되어 있지 않다. C4 감사가 지적한 "회당 단가를 한 건도 산출하지 않는 파서가 계약을 100% 준수한다"의 웹 레이어 대응물이다.

### P4. C7 FORBID-1의 `when` 이 너무 넓어 운영 기능이 구현 불가 → 예외가 확정적으로 발생
C7 FORBID-1은 "웹(apps/web) 또는 공용 API 레이어"의 base 테이블 접근을 DB 롤 권한으로까지 차단한다. 그런데:
- **O2 검수 큐**는 정의상 비공개 레코드를 봐야 한다 → 뷰로 구현 불가.
- **O1 `price_coverage`** 는 분모에 비공개 업체가 필요하다 → 뷰로 구현 불가.
- **W1 FORBID-4**(app/** → DB import 금지)는 W2·W3의 `app/api/**` 핸들러를 구현 불가로 만든다.

세 곳 모두에서 예외가 필요하고, **예외를 파는 순간 공개면 보호도 함께 뚫린다.** 원칙 2가 경고한 "무조건 금지는 반드시 깨지고, 깨지는 순간 다른 금지도 협상 가능해진다"의 교과서적 사례다.
→ **PRD §2가 요구한 공용 API 레이어(`packages/api`)를 소유하는 태스크가 계획에 없다는 것이 근본 원인.** 접근 통제를 경로가 아니라 **DB 롤 단위**로 재설계하고, 내부 운영용 읽기 롤을 별도 정의해야 한다.

### P5. medical_wellness 조건부 FORBID — 걸린 곳은 5건, 그러나 `when` 의 판정 대상이 3가지

| 태스크 | 조항 | `when` 의 판정 대상 |
|---|---|---|
| W2 | FORBID-6 | "카드의 **카테고리**" |
| W3 | FORBID-3 + REQ-8 | "**카테고리**" |
| W4 | FORBID-6 | "**매니페스트 행**의 카테고리" |
| W5 | FORBID-2 | "**category_axis**" |
| O2 | FORBID-6 | "**category_axis**" |
| **W1** | **없음** | — |

문제 넷:
1. **F2에 `category`/`category_axis` 컬럼이 정의되어 있지 않다.** 판정 대상 필드가 실재하지 않는다.
2. **D4 `medical_scope.yaml` 의 업종 enum(정본)을 참조하는 계약이 0건이다.** 축 오분류 1건이면 5개 조항이 동시에 회피된다.
3. **W4의 `when` 은 페이지의 축을 보고 결과집합의 업체 축을 보지 않는다** — 라벨만 바꾸면 우회.
4. **W1이 소유한 공용 `generateMetadata`·JSON-LD 빌더가 무검사다.** title·description은 검색 스니펫으로 사이트 밖에 유통되는데, D4 사전 검사는 W3·W4·W5의 렌더 스캔에만 있다.

### P6. 지표 정의 체계의 부재가 H1·H4·H5·H7 판정을 전부 무효화한다
- **H1** — `price_coverage` 분모가 PRD(수집 표본 전체) / lean canvas(수집 업체) / C7 REQ-7(**공개 업체**)에서 상충. C7 정의를 쓰면 **커버리지가 구조적으로 100%에 수렴**한다. G1의 3구간 판정(25% 임계)은 O1 계약 어디에도 없다.
- **H4** — `price_block_seen` 의 카운트 조건(어떤 price_state, 요금제 0건 포함 여부)을 정의한 계약이 없다. W3와 W6이 서로를 참조하지 않는다.
- **H5** — 필터 사용 이벤트를 수집하는 태스크가 없다. W2가 표면을 만들고 O1이 지표를 요구하지만 중간이 비어 있다.
- **H7** — W6의 식별자는 `session_id` 뿐이고 FORBID-3이 안정적 식별자를 제한한다. **4주 재방문 판정 입력이 존재하지 않는다.**
- **CTR** — Search Console 연동을 W1이 O3로 넘겼고 O3가 받지 않았다.
- `KM-*`·`NSM-*` ID가 어느 문서에도 정의되지 않았는데 **O1 REQ-3이 그 문서 표를 파싱하는 CI를 만든다.** lean canvas는 상태가 "확정 대기"다.

### P7. DAG 표기·정합성 (10건 전부)
- **ID 정본 미준수 10/10** — 전 계약이 축약형(`W1`,`F2`,`C7`)을 쓴다. C 배치는 완전형(오타 포함)을 쓴다. **두 규약이 공존하므로 DAG 자동 검증이 어느 쪽으로도 성립하지 않고, 게이트 선행 검사를 자동화할 수 없다.**
- **폐기된 F3 참조 4건** — W1·W2·W3 `depends_on`, O3 `parallel_with`. DS1·DS3·DS4·DS5·DS6가 실제 소유자다. **특히 W3의 가격 비교 블록은 DS4-PRICE-COMPARE-CARD(★시그니처 컴포넌트)와 완전히 겹치는데 상호 참조가 0이다** — 같은 컴포넌트를 두 태스크가 각자 만든다.
- **비대칭 엣지 3건** — W5 `blocks:[W4]`(W4에 없음) / W7 `blocks:[O2]`(O2에 없음) / F2 `blocks:[W3]`(W3에 없음).
- **누락 의존 4건** — W4←C7(**DAG 정본은 이미 수정되었으나 계약은 미수정, 게다가 `parallel_with:[C7]` 로 반대 선언**) · W4←D2 · W3←D4 · W5←D4.
- **게이트 선언 불일치** — 동일 Phase 3에서 W1·W2·W3는 `gate: null`, W5·W6·W7은 `[G1,G2,G3]`.
- **게이트 역행 2건** — O1·O2의 `gate: G4` 가 각자의 존재 이유(G1 판정 관측 / G4 미달 방지)와 시간 순서상 모순.

### P8. 자기 출제·자기 채점 (R-6) — 3건
W4 REQ-3(유사도 표본 100, 표집 절차·홀드아웃 없음) · W6 REQ-6(봇 UA 픽스처 자작) · O1(골든 픽스처 자작). C1-C7 감사의 P2가 웹 배치에서도 반복된다. 규격 개정(R-6)이 개별 계약에 아직 반영되지 않았다.

### P9. 소유자 없는 작업 6건 (계약 사이의 빈 공간)
계약 A가 "B 소관"이라고 배제했는데 B가 받지 않은 항목들. 어느 계약을 개별로 읽어도 발견되지 않는다.
1. **W7 삭제·정정 요청의 처리** — W7 out_of_scope → O2, O2는 큐 정의에 미포함. **법적 리스크.**
2. **Search Console 연동** — W1 out_of_scope → O3, O3에 없음. O1 CTR 지표 불능.
3. **ISR 캐시 무효화** — 어느 계약에도 없음. G4 실효성 상실.
4. **`is_public` / 품질 스코어 컬럼 생성** — C7 out_of_scope → F2, F2 산출물에 없음.
5. **W4 프로덕션 색인 활성화 배포** — W4 done_when이 "별도 배포"라고만 씀.
6. **에디터 리포트 콘텐츠 생산 20~30건** — W5 out_of_scope, 대체 태스크 없음. H6 판정 불능.

## 전달 전 필수 조치 (우선순위)

1. **P1 `is_public` 정합화 라운드** — 7개 계약이 동시 블로커. F2 `visibility` ENUM을 정본으로 확정하고 비공개 사유별 취급을 명시. **이것 없이는 W2·W4·W5·W7·O1·O2를 전달할 수 없다.**
2. **W3에 공개 판정 FORBID 신설** — 단일 조항으로 가장 큰 우회 경로가 닫힌다.
3. **C7 REQ-1 ↔ O2 REQ-4 충돌 해소** — 판정 레이어(C7) / override 레이어(O2) 분리 + `public_venue` 뷰가 결합. **부수 조건: C7에 뷰 필터 REQ 신설**(C1-C7 감사 §2-1과 동일 결론).
4. **W4 `depends_on` 에 C7 추가 + `parallel_with` 에서 제거** — DAG 정본과 반대 방향인 상태로는 전달 불가.
5. **W7 처리 소유자 확정** — 접수만 되고 처리되지 않는 경로는 법적 리스크이며, O3 알림이 공허해 자동 탐지도 0이다.
6. **O1 지표별 데이터 소스 실재 확인** — 최소 3개 지표(H5·H7·CTR)의 소스가 계획에 없다.
7. **ISR 캐시 무효화 소유자 지정** — G4가 빌드 시점에만 존재하는 게이트가 되는 것을 막는다.
8. **공용 API 레이어 태스크 신설** — P4의 근본 원인이며, W1 FORBID-4·C7 FORBID-1의 예외 압력을 제거한다.
9. **ID 정본 표기 규약 통일 + F3 → DS 노드 교체** — 전 계약 일괄.
