## §0 — 매니페스트가 보지 못한 것 (기계 검증의 사각)

기계 검증을 재계수하지 말라는 지시를 지키되, **기계가 못 본 것**은 보고한다.

1. **DS0 `parallel_with` 가 파서에 의해 통째로 소실됐다.**
   ```yaml
   parallel_with: [D1-PRICE-AVAILABILITY-SPIKE, D2-…, D3-…,
                   D4-…, F1-REPO-SCAFFOLD]
   ```
   `LIST_INLINE` 정규식은 `]` 로 끝나는 **한 줄** 인라인 리스트만 잡는다. 줄바꿈된 DS0의 리스트는 매치되지 않아
   `docs/tasks.json` 의 `DS0.parallel_with == []` 로 기록됐다(실측). 그 결과 **`D1-PRICE-AVAILABILITY-SPIKE`(정본 레지스트리상 "폐기 · 신규 참조 금지") 참조가 검사를 통과했다.**
   → 매니페스트 스크립트의 사각이자, DS0 계약의 폐기 태스크 참조 위반이다. 둘 다 고쳐야 한다.

2. **`blocks → depends_on` 방향은 아무도 검사하지 않는다.**
   `tasks_manifest.py` 는 `depends_on → blocks` 한 방향만 본다. 그래서 **DS0.blocks 에 `DS3-BASE-WIRING` 이 있는데 DS3.depends_on 에는 DS0이 없다**(DS3.depends_on = `[F1, DS1]`)는 비대칭이 통과했다.
   DS0이 G5 판정의 유일한 근거인데 DS3은 그 판정에 의존하지 않는다고 선언한 상태다.

3. **`traces_to` 는 전혀 검증되지 않는다.** 아래 각 태스크의 규격 위반 항목 참조.

**공격 결과**

- **A 악의적 준수** — 시도: "REQ를 전부 지키면서 판정을 원하는 쪽으로 몰 수 있는가?" `rule.lock` 선고정(REQ-1)과 FORBID-5가 사후 조정을 막으므로 **설계상은 방어됨**. 그러나 실제 종결은 그 반대로 갔다 — 룰 파일도 락도 없이 산문 보고서 1건으로 종결됐고, 계약 헤더가 그 사실을 자인한다("계약이 명시한 다분할 구조 대신 단일 실사 보고서 1건으로 제출"). **사전 잠금 장치를 통째로 건너뛴 것이 결함이다.** 다음 조사 태스크가 이 관용구를 학습한다(원칙 2 붕괴 경로).
- **B 조건 회피** — FORBID-2의 `when` 은 "근거가 스크린샷·블로그·Figma·요약문만"이다. 실제 보고서의 근거는 **URL 문자열과 인라인 인용문**이다. tarball sha256 대조는 부록에 "방법"으로만 적혀 있고 **스냅샷 파일·해시값이 리포에 커밋되어 있지 않다.** URL은 png가 아니므로 FORBID-2의 확장자 검사는 통과한다 → 조건을 정확히 비껴간다. 원격 URL은 언제든 내용이 바뀐다.
- **C 탐지 무력화** — detect 5건 전부 존재하지 않는 스크립트. 탐지율 0. done_when 의 "FORBID-1~5 각각에 대응하는 --check 서브커맨드가 의도적 위반 픽스처에서 non-zero exit 하는 것을 확인" 역시 미수행.
- **D 지름길 유도** — 실제로 발생한 지름길이 바로 "산출물 형식을 계약과 다르게 내고 사후에 기록만 남기기"다. 계약은 이 경로를 막는 조항이 없다. 헤더가 "사후에 REQ를 산출물에 맞춰 고쳐 쓰지 않는다"고 선언한 것은 정직하나, **그것이 미충족을 충족으로 만들지는 않는다.**
- **E DAG 정합성** — §0-1·§0-2의 2건. 추가로 `gate: null` + "이 태스크가 G5의 입력을 산출한다"는 정합적. DS2 폐기 처리는 정상.
- **F 존재 이유** — G5 판정 자체는 DS1·DS3의 전제이므로 존재 이유는 **실재한다.** 다만 `traces_to: [G5, H4, S1]` 중 H4(가격 블록 전환율)와의 연결은 근거가 없다 — 실사 보고서 어디에도 H4 검증에 기여하는 산출물이 없다. 형식 요건은 충족하나 실질 추적성은 G5 하나뿐이다.

**하류 인용 가능성 (팀 리드 지목 항목: D4와 동일 결함인가?)**

**그렇다. 같은 결함이 있다.** D4는 1차 감사 후 정본 경로(`packages/legal/medical/dist/exported_rules.json`)·스키마(`rules.schema.json`)·`rule_id` 체계를 고정했다. DS0은 하나도 고정하지 않았다.

- DS1은 `§2.2 · §5.2 · §8 · §9.1` 을, DS3은 `§6 · §7 · §9.2` 를, DS5는 `§2.3` 을 **절 번호로만** 인용한다. 절이 하나 삽입되면 전 하류 인용이 조용히 어긋난다. 앵커도 ID도 버전도 없다.
- `@seed-design/css@2.3.0` 등 **버전은 부록 산문에만 있고 기계 판독 가능한 형태(json/lock)로 고정되어 있지 않다.** DS1 REQ-8·FORBID-5가 "정확한 x.y.z 고정"을 요구하는데, **그 x.y.z 가 무엇인지 계약이 못박지 않았다** → 구현자가 임의 버전을 골라 핀 고정하면 준수다. carrot 변수 집합이 릴리스마다 늘어난다는 FORBID-5의 근거가 그대로 실현된다.
- 보고서 스스로 "실사 기준일 2026-08-02~03 · 주당 최대 48커밋이므로 수 주 내 사실관계가 바뀔 수 있다"고 적었다. **유효기간이 명시된 판정인데 재검증 트리거가 없다.**
- **NOTICE 원문 스냅샷이 리포에 없다.** carrot 교체 의무의 유일한 법적 근거가 원격 raw.githubusercontent URL 인용문이다.

## DS1-TOKEN-LAYERS — REVISE

**규격 위반**

- `[요구사항] REQ 하나에 복수 요구가 결합(R-4)` — REQ-2("동일 hex 0건" **그리고** "단계 수 일치"), REQ-4(참조 중복 0 **그리고** 대비 ≥1.5 **그리고** stroke-width 2종 이상 — 3중 결합), REQ-7(폰트 크기 하한 **그리고** pairs.json role 사용 제한).
- `[금지사항] when 이 '항상'에 해당` — FORBID-3 `when: "brand.css 또는 semantic.css 에서 토큰 값을 기술할 때"`. 이건 조건이 아니라 **파일 지정**이다. 그 파일에서 값을 쓰는 모든 행위가 대상이므로 무조건 금지다(§3.4 안티패턴).
- `[금지사항] 계약이 자기 PR을 차단` — **아래 공격 A 참조. 가장 중대한 위반이다.**
- `[요구사항] 품질 임계 REQ의 표집 절차 부재(R-6)` — REQ-6은 "pairs.json 전수"라고 쓰지만 **pairs.json 의 모집단 하한이 계약 어디에도 없다.** 계약 헤더가 이 문제를 자인하고 DS6에 위임하는데, 위임은 시점이 어긋난다(아래 C).

**공격 결과**

- **A 악의적 준수 (2건, 둘 다 치명적)**

  **A-1. carrot 교체가 "동일 hex 0건"으로만 정의되어 있다.**
  REQ-2: *"brand-palette.json 의 glowmate 브랜드 값 중 어느 것도 seed 원본 carrot 값과 동일하지 않으며(동일 hex 0건)"*.
  → `#FF6F0F` 를 `#FF6F0E` 로 바꾸면 동일 hex 0건, 단계 수 일치, REQ-1 전량 재정의 충족, FORBID-1 통과. **계약 100% 준수 상태로 화면은 당근 오렌지 그대로다.**
  이 태스크의 존재 이유("NOTICE의 오인 유발 금지 조항")가 **문자열 동일성으로 환원되어 무력화**됐다. 상표 리스크는 hex 문자열이 아니라 **보이는 색**에서 발생한다.
  → 필요한 것은 지각적 거리 임계다: 각 단계에서 carrot 원본 대비 **CIEDE2000 ΔE ≥ N** 또는 **HSL 색상각 차 ≥ N°**. 계약 본문에 수치를 못박아야 한다(§3.4 "사전 설정 무방비" 회피).

  **A-2. FORBID-3이 REQ-1을 구조적으로 불가능하게 만든다 (자기 차단).**
  - REQ-1: brand.css 가 `--seed-color-palette-carrot-*` **전량을 재정의**해야 한다.
  - FORBID-3: brand.css 에서 `#hex · rgb() · oklch()` **리터럴 금지**, `var(--…)` 참조만 허용. detect는 "선언 값이 `var(--…)` 형식이 아닌 항목 수 = 0".
  - 그렇다면 glowmate 팔레트의 **실제 색 값(리터럴)은 어느 CSS 파일에 들어가는가?**
    - `brand-palette.json` 은 JSON이라 CSS 변수를 만들지 못한다. 그리고 **DS2(Style Dictionary)가 폐기되어 생성 단계가 없다** — DS1 스스로 "생성 단계가 없으므로 원천은 CSS 파일 그 자체다"라고 못박았다.
    - DS3 REQ-6은 `--*` 를 **정의**할 수 있는 파일을 4개(seed base / tailwind4-theme / brand.css / semantic.css)로 화이트리스트한다. 새 CSS 파일을 만들 여지가 없다.
  - **결론: 리터럴이 들어갈 수 있는 유일한 곳이 brand.css 인데 FORBID-3이 그것을 금지한다.** 개발 에이전트는 반드시 우회하고(예외 주석·검사 회피 포맷), **첫 토큰 PR에서 우회 관용구를 학습한다.** §3.4 마지막 안티패턴 그대로다.
  - 부수 결함: `brand-palette.json` 은 생성원이 아니면서 DS3 REQ-5의 대조 기준이다 → **팔레트 값의 원천이 2곳(brand.css, brand-palette.json)**. 둘의 일치를 검사하는 REQ가 DS1에 없다(DS3 REQ-5가 런타임에서 우연히 잡을 뿐).

  **A-3. pairs.json 을 2행만 채우면 REQ-6이 만점이다.** "전수 평가"는 모집단이 구현자 소유일 때 아무 보증이 아니다. 특히 **REQ-3이 만드는 가격 상태 12토큰의 (fg,bg) 4쌍이 pairs.json 에 등재되어야 한다는 REQ가 없다** → 대비 2:1짜리 저신뢰 배지가 DS1 CI 초록으로 통과한다.

**공격 결과**

- **A 악의적 준수**

  **A-1. 화이트리스트가 Tailwind v4 기본 테마를 배제한다 → 정상 구현이 곧 위반.**
  REQ-1이 요구하는 `globals.css` 는 `@import "tailwindcss";` 로 시작한다. Tailwind v4는 `@theme` 로 `--color-red-500`, `--spacing-*`, `--text-sm` 등 **수백 개의 커스텀 프로퍼티를 정의**한다. 그 정의 출처 파일은 `tailwindcss` 패키지이고 **화이트리스트 4개(seed base / tailwind4-theme / brand.css / semantic.css)에 없다.**
  → REQ-6 "화이트리스트 밖 정의 0건" 이 **첫 커밋부터 실패**한다. 개발 에이전트가 취할 수 있는 행동은 둘뿐이다:
  (a) 화이트리스트에 `tailwindcss` 를 추가 → **그 순간 이 워크스트림 최상위 FORBID의 방어력이 사라진다.** 왜냐하면 shadcn 기본 테마 변수도 Tailwind `@theme` 문법으로 들어오는데, 출처가 어느 파일인지 빌드된 CSS에서 구분하기 어려워지기 때문이다.
  (b) 검사를 "우리 소스 파일만 스캔"으로 축소 → node_modules 유래 정의를 안 보게 되어 **`@seed-design/css` 와 shadcn 의 공존조차 못 잡는다.**
  → **팀 리드가 지목한 "토큰 소스 2개 공존" 최상위 위험의 탐지 수단이, 정확히 이 지점에서 협상 대상이 된다.**

  **A-2. 폰트를 아예 로드하지 않으면 REQ-4가 만점이다.**
  REQ-4: "외부 폰트 요청 0건 **그리고** 폰트 전송 바이트 ≤ 300,000". 폰트가 0바이트 로드되면 둘 다 충족이다. 그리고 **어떤 REQ도 "본문 텍스트의 computed `font-family` 가 Pretendard 다"를 검사하지 않는다.** REQ-2는 `@font-face` 선언 수(92)만, REQ-8은 텍스트 존재만 본다.
  → `pretendard.css` 를 만들어 커밋하되 `layout.tsx` 에서 import 하지 않으면 8개 REQ 전부 통과, 화면은 시스템 폰트. FORBID-3의 `because` 가 우려한 "시스템 폰트 폴백으로 DS6 검사와 실제 화면이 어긋나는" 상태가 **위반 없이** 성립한다.

  **A-3. 스모크 라우트의 내용 하한이 없다.** 다이나믹 서브셋은 **페이지에 등장하는 글리프**에 따라 chunk 수가 결정된다. 스모크 라우트에 한글을 10자만 넣으면 chunk 1~2개(≈33~66KB)로 300KB를 여유롭게 통과한다. 실제 업체 리스트 페이지는 수백 글리프를 쓴다. **REQ-4는 실환경 하한처럼 보이지만 측정 대상이 구현자 소유라 아무것도 보증하지 않는다.**

  **A-4. REQ-5도 같은 구조다.** "렌더된 페이지의 계산 스타일에 seed 원본 carrot hex 가 0건" — 스모크 라우트가 brand 계열 색을 **하나도 쓰지 않으면** 자명하게 0건이다. seed 시맨틱 토큰(`--seed-color-fg-brand` 등)이 palette 변수를 참조하지 않고 hex를 직접 물고 있는 경우(실사 §9.3-1이 "미실증"으로 남긴 바로 그 리스크)를 **잡을 수 있는 유일한 검사가 자명하게 통과**한다.

- **B 조건 회피** — FORBID-2 `when`: "니즈 태그의 슬러그 목록이나 한국어 라벨이 컴포넌트에서 필요해진 경우". 회피: 라벨 배열이 아니라 **`Record<slug, label>` 객체 리터럴**이나 `slug.replace('-', ' ')` 같은 파생 함수를 쓰면 "배열 리터럴 grep"을 빠져나간다. detect가 자료구조 형태(배열)에 묶여 있다.

- **F 존재 이유** — `H5`(니즈 태그 필터 사용률)와 FilterBar·NeedsTagChip의 연결은 직접적이다. FORBID-3의 `because`("색상 단독 구분이면 H5가 가설 문제인지 UI 결함인지 구분 불가")는 **가설 검증 가능성과 컴포넌트 요구를 정확히 잇는다 — 이 워크스트림 최고 수준의 존재 이유 서술.** 다만 A-1이 성립하면 그 논증 전체가 무의미해진다.

## DS6-A11Y-GATE — REVISE

> 이 태스크는 **자기 실패 모드를 스스로 정확히 진단**했다(설계 전제의 "게이트가 비어 있게 되는 3가지 경로"). 그 자기 진단은 이 배치 전체에서 가장 수준 높은 서술이다. **그러나 진단한 3경로 중 ②(픽스처만 검사)를 실제로는 막지 못한다.**

**규격 위반**

- `[금지사항] detect 가 참조하는 대상이 실재하지 않음` — 2건. 아래 공격 C-1·C-2.
- `[요구사항] acceptance 가 statement 를 검증하지 못함` — REQ-8 "브랜치 보호 필수 체크에 등록"의 acceptance가 **워크플로 파일 파싱**이다. 브랜치 보호는 워크플로 YAML에 존재하지 않는 GitHub 리포 설정이다. **검증 불가능한 acceptance.**
- `[요구사항] REQ 하나에 복수 요구 결합(R-4)` — REQ-3(케이스 수 하한 **그리고** 총합 하한), REQ-7(5개 규칙 묶음), REQ-8(job 존재 **그리고** 필수 체크 **그리고** axe 0건).
- `[요구사항] 실환경 하한이 명목상 충족(R-7)` — 아래 공격 A-1.

**공격 결과**

- **A 악의적 준수 (팀 리드 지목: "아무 컴포넌트도 렌더하지 않으면 위반 0건인가?")**

  **A-1. 게이트가 프로덕션 화면을 영원히 보지 않는다 — R-7의 실질적 미충족.**
  - REQ-6의 실환경 대상은 `targets.json` 이고, DS6 머지 시점의 유일한 항목은 **DS3의 `wiring-smoke`** — `(dev)` 세그먼트의 `noindex` 임시 라우트로, 프리미티브 3종만 렌더한다.
  - DS7이 그것을 제거하고 **비배포 프리뷰 앱** 라우트로 교체한다(DS7 REQ-6·FORBID-5).
  - **실측 확인: `W1`~`W9` 계약 전체를 grep한 결과 `targets.json`·`a11y:check`·`ds-a11y` 를 언급하는 W 계약이 0건이다.**
  - → **W2 리스트·W3 상세·W4 조합 랜딩이 `targets.json` 에 등재될 의무가 어느 계약에도 없다.** 게이트는 영구히 "개발용 라우트 1개 + 구현자가 쓴 케이스"만 본다.
  - 이것이 정확히 DS6 자신이 표에 적은 **② 경로(픽스처만 검사 → 컴포넌트는 통과하는데 실제 페이지는 미달)** 다. REQ-6은 그 경로를 막았다고 선언하지만, 막은 것은 "targets가 **비어 있는** 상태"뿐이고 "targets가 **의미 없는** 상태"는 막지 못한다.
  - 실제 페이지에서만 발생하는 실패(이미지 위 텍스트, sticky 하단 바의 터치타깃 겹침, 긴 업체명 리플로, 스크롤 컨테이너 내 대비)는 **전부 게이트 밖**이다.

  **A-2. `pair-coverage`(REQ-5)의 관측 규칙이 계약에 없다.** "실제 렌더에서 관측된 (전경색, 배경색) 조합" — **어떤 노드를 관측 대상으로 삼는지, 배경이 투명일 때 조상 탐색을 어디까지 하는지, 이미지·그라디언트 배경을 어떻게 처리하는지**가 정의되지 않았다. 구현자가 "명시적 비투명 배경을 가진 노드"로 좁히면 관측 집합이 극적으로 줄어들고, **DS1의 pairs.json 자기 출제를 잡겠다는 R-6 방어가 그대로 무력화**된다. 시험지를 좁히지 못하게 막는 장치가, 채점 범위를 좁힘으로써 뚫린다.

  **A-3. REQ-3의 하한이 약하다.** "케이스 수 ≥ 컴포넌트 디렉터리 수". 컴포넌트 5개 × 케이스 1개씩이면 충족. DS5가 ≥3을 별도로 요구하나 **DS4는 4상태 4케이스만, 그 외 컴포넌트 규정 없음**. 게이트 자신의 하한은 사실상 "0이 아니면 통과".

- **B 조건 회피** — FORBID-1 `when`: "`a11y:check` 가 실패한 상태에서 이를 통과시키려는 변경을 만들 때". 판정 가능한가? "통과시키려는 의도"는 관측 불가다. 실제 detect는 "diff에 임계 하향 또는 항목 삭제 + 라벨 없음"이므로 detect가 `when` 보다 좁고 명확하다 — **문면은 의도 기반(판정 불가), 집행은 diff 기반**. `when` 을 diff 조건으로 재작성해야 한다.
  회피 경로: 페어를 **삭제**하지 않고 `role` 을 `body`(7:1)에서 `secondary`(4.5:1)로 **강등**하면 임계 하향도 삭제도 아니다. FORBID-1이 못 잡는다.
- **C 탐지 무력화**

  **C-1. FORBID-4의 detect가 존재하지 않는 job에 의존하고, DS6는 그것을 만들 수 없다.**
  detect: *"CI job `lint` — 워크플로/소스 diff 에 `continue-on-error` · `|| true` · `eslint-disable` 신규 추가가 있으면 실패"*.
  그런데 DS6의 `touches` 는 `.github/workflows/ci.yml` 에 대해 **"job `ds-a11y` 추가만 (기존 job 수정 금지)"** 이고, `out_of_scope` 는 *"F1 이 만든 기존 CI job · eslint 프리셋의 수정"* 을 명시적으로 배제한다.
  → **이 diff 검사를 DS6가 구현할 수 없다.** F1이 제공한다는 보장도 계약에 없다(F1을 `depends_on` 하지도 않는다). `on_violation: block_merge` 인데 집행자가 없다(§3.4 마지막 항목).

  **C-2. REQ-8·FORBID-4의 "브랜치 보호 필수 체크" 검증 수단이 없다.** 워크플로 파싱으로는 원리적으로 확인 불가. GitHub API(`/repos/{o}/{r}/branches/{b}/protection`) 조회나 리포지토리 ruleset 파일 커밋이 필요하다. **DS4·DS5·W 다수가 유일 탐지 수단으로 지목하는 job이 "필수 체크로 등록되어 있다"는 사실을 아무도 검증하지 않는다.**

  **C-3. FORBID-1의 라벨 자가 부여** — DS1 FORBID-4와 동일. CODEOWNERS 보호는 **파일 승인**을 강제하지만, `threshold-change-approved` **라벨은 작성자가 스스로 붙일 수 있다.** 두 장치가 OR로 묶여 있어 약한 쪽이 실효 강도를 결정한다.

  **C-4. 잘 만든 detect도 있다 — 기록.** REQ-2/FORBID-2의 **변이 테스트**(constraints 5개 키를 극단값으로 치환한 5회 실행이 전부 실패해야 함)는 "검사가 실제로 임계를 읽고 있는가"를 검증하는 정확한 메타 검사다. - **D 지름길 유도** — (1) `targets.json` 에 가벼운 라우트만 유지(A-1), (2) 관측 규칙을 좁게 구현(A-2), (3) role 강등(B), (4) 라벨 자가 부여(C-3), (5) `eslint-disable` — C-1로 인해 실제로는 막히지 않는다.

**필수 수정 사항**

1. **REQ-6을 실환경 하한답게 재작성(최우선).** "`targets.json` 은 **`apps/web` 의 프로덕션 라우트(= `(dev)` 세그먼트가 아니고 `noindex` 가 아닌 라우트)를 최소 1개 포함**해야 하며, 0이면 exit 1." 그리고 **W1이 최초의 프로덕션 라우트를 등재할 의무를 W1 계약에 신설하도록 상신**, 이후 W2·W3·W4는 자기 라우트 등재를 done_when에 포함. 현재 상태에서 이 게이트는 프로덕션 화면을 한 번도 보지 않는다.

| **DS0 산출물이 인용 가능하게 고정됐는가** | **아니다. D4와 동일한 결함.** 정본 경로·스키마·버전·해시 전부 미고정. 하류가 절 번호(§2.2·§9.2 …)로 인용하고, 패키지 버전은 산문 부록에만 있으며, NOTICE 원문 스냅샷이 리포에 없다. 보고서 자신이 "수 주 내 사실관계가 바뀔 수 있다"고 적었는데 재검증 트리거가 없다. |
| **carrot 교체가 REQ로 강제되는가** | **강제된다**(DS1 REQ-1·FORBID-1, `node_modules` 실물 파싱 + 차집합 0). 실사 보고서에서는 "권고"였던 것이 계약에서 의무로 격상된 것은 옳다. **그러나 "교체"의 정의가 문자열 비동일성뿐이라 실질 방어가 없다**(1비트 시프트). 추가로 **Apache-2.0 §4 귀속 고지(LICENSE 사본 + NOTICE 동봉) REQ가 DS1·DS3 어디에도 없다** — Pretendard OFL 고지는 있는데 seed 것만 증발했다. |

### 체계적 결함 패턴 (2건 이상 반복)

**P1 — "0이면 자명하게 통과"하는 전칭명제·집합 연산 (DS5 3건 · DS7 2건 · DS3 2건 · DS6 1건)**
`빈 배열 → 칩 0개` / `data-price-state 노드가 DS4에서만 생성` / `대칭차집합 = 0` / `원본 carrot hex 0건` / `외부 폰트 요청 0건`. **부정형 조건은 대상이 0일 때 항상 참이다.** 이 배치의 REQ는 상한·부재·일치를 잘 쓰지만 **하한을 거의 쓰지 않는다.** 원칙 2.5는 "숨김 FORBID에 positive REQ를 짝지어라"인데, 실제로 필요한 것은 **모든 부정형 acceptance에 대응하는 최소 개수 하한**이다.
→ 처방: 각 부정형 acceptance 옆에 "검사 대상 수를 stdout 출력하고 0이면 exit 1"을 규약으로 삼는다. DS1 REQ-1·REQ-6과 DS6 REQ-3은 이미 이 형태다 — **같은 리포 안에 좋은 관용구가 있는데 확산되지 않았다.**

**P2 — 측정 대상을 구현자가 소유 (DS1 pairs.json·typography 토큰 집합 · DS3 스모크 라우트 내용 · DS4·DS5 `*.cases.tsx` · DS6 관측 규칙 · DS7 프리뷰 엔트리)**
R-6은 "평가 데이터의 표집 절차를 REQ에 명시"를 요구한다. 이 배치는 **품질 임계가 있는데 표집 절차가 있는 REQ가 0건**이다. DS6가 "관측 조합 ⊆ pairs.json" 으로 DS1의 자기 출제를 잡겠다고 선언했으나, **관측 규칙 자체가 미정의**라 채점 범위를 좁혀 같은 구멍으로 빠져나간다.
→ 처방: 케이스·라우트·페어의 **내용 하한을 계약이 고정**한다(무엇을 렌더해야 하는가, 어떤 노드를 관측하는가).

**P3 — detect가 미선언 병렬 태스크의 산출물 (DS4 2건 · DS5 2건 · DS3 1건 · DS6 1건 · DS7 1건)**
DS4 REQ-7/FORBID-4 → DS6, DS5 REQ-1/FORBID-3 → DS6, DS3 FORBID-2 → 소유자 없는 `ds-wiring` job, DS6 FORBID-4 → 자기가 못 만드는 `lint` job diff 검사, DS7 REQ-6 → DS6.
규격 체크리스트 *"detect 가 참조하는 대상이 선행 태스크 산출물에 실재하지 않음"* + *"`block_merge` 인데 집행할 CI job이 없음"* 의 반복이다. **DS6가 `parallel_with` 로 선언된 것이 근원** — 다른 태스크의 detect를 공급하는 태스크는 병렬일 수 없다.
→ 처방: **DS6를 DS4·DS5·DS7의 `depends_on` 으로 승격.** DS6 자신이 "이 태스크가 다른 태스크들의 detect를 공급한다"고 선언했으므로 DAG가 그 선언을 따라야 한다.

**P4 — 우회 예외를 규칙 안에 넣지 않아 계약이 자기 PR/형제 PR을 차단 (DS1 FORBID-3 · DS3 REQ-6 · DS7↔DS6 FORBID-1 · DS6 FORBID-4)**
DS1은 `packages/config/test/workspace.test.ts` 1건 갱신을 예외로 명시하는 모범을 보여줬는데, **같은 계약의 FORBID-3에서는 그 원칙을 적용하지 않았다.** §3.4 마지막 안티패턴("개발 에이전트가 반드시 우회하며 우회 관용구를 학습한다")이 이 배치에 4건 있다. 특히 DS7이 `threshold-change-approved` 라벨로 DS6를 우회하는 경로는 **임계 보호 장치를 정상 작업에서 무력화하는 학습**을 만든다.

**P5 — 승인 게이트가 라벨 자가 부여로 무력 (DS1 FORBID-4 · DS6 FORBID-1)**
두 계약 모두 `threshold-change-approved` 라벨을 유일한/병렬 예외 통로로 둔다. GitHub 기본 설정에서 **PR 작성자가 자기 라벨을 붙일 수 있다.** 같은 리포의 F6 FORBID-3은 "CODEOWNERS 승인자 ≠ PR 작성자를 GitHub API로 조회"라는 정확한 형태를 이미 갖고 있다 — **강도가 계약마다 두 단계 다르고, 약한 쪽이 전체 실효 강도를 결정한다.**

**P6 — `traces_to` 원장 이원화 및 유령 ID (DS0 `G5` · DS4 `KM-qualified-lead` · DS1·DS4 `S1` · DS5 `S2`)**
1차 감사(C1~C7)가 `KM-price-coverage` 로 4건 지적한 것과 **동일 패턴이 DS4에서 재발**했다. G5는 이 워크스트림 전체를 가르는 게이트인데 **PRD §4에 없다**(G1~G4뿐). 게이트·지표의 정본 원장을 PRD 하나로 통일하지 않으면 `traces_to` 자동 검증이 영구히 불가능하다.

**P7 — dag_amendment 상신은 계약에만 있고 `03-task-dag.md` 는 미갱신 (DS5 · DS6, DS7은 상신조차 안 함)**
DS5·DS6가 DAG 결함을 정직하게 상신한 것은 좋은 규율이다. 그러나 **정본 문서(`03-task-dag.md` Phase 1.5 표 149~152행)가 갱신되지 않아 문서와 계약이 갈라져 있다.** 매니페스트는 계약 기준으로 통과하므로 이 불일치는 기계가 못 잡는다. 팀 리드 결재 후 문서 반영이 필요하다.
