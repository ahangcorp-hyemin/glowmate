# 스펙: 컨시어지 역경매 베타 (#72) — v1 상세
근거: PRODUCT_PLAN_V2 §3, 모두닥 캡처(도착 프레이밍·연락처 지연 공개), Pluto 패턴. 기존 자산 재사용이 설계 원칙.

## 0. 한 줄 정의
유저는 조건만 입력하고 전화하지 않는다. 24시간(영업일) 안에 **병원 3곳의 구조화된 견적**이 도착하고, 유저가 병원을 고르기 전까지 연락처는 병원에 공개되지 않는다. 베타에선 회신을 **컨시어지(운영자 전화)**로 수집한다 — 이 전화 1통이 곧 ①SKU 엔진의 데이터 수집이기도 하다(부산물 설계).

## 1. 유저 플로우 (화면 5개, 기존 UI 최대 재사용)
```
[진입 3곳]                          [신청]              [완료]            [결과]               [연결]
견적 결과 "실제 견적 받아보기" ─┐
병원찾기 상단 유도 카드 ────────┼→ 조건 위저드 1장 → 도착 예고 화면 → 견적 3장 비교 화면 → 방문예약 플로우 합류
홈 액션 카드 ──────────────────┘   (프리필+메모+동의)                    (/saved 내역 상주)     (기존 visit_requests!)
```
1. **진입**: 견적 결과 요약에 주 CTA "이 조합, 실제 견적 받아보기 — 전화는 저희가 할게요". 진입 시 concerns·age·budget·시술이 **자동 프리필**(모두닥 '최근 설정한 조건' 문법).
2. **신청 위저드(1화면)**: 프리필 조건 요약 카드(수정하기) + 추가 입력 3개만 — 희망 지역(REGIONS 픽커 재사용) / 다운타임 가능일(없음·주말만·1주·상관없음) / 자유 메모(500자, "병원에 전달하고 싶은 말"). 회신 채널: 기본 "앱에서 확인"(무가입 유지, localStorage requestId) + 선택 "문자로도 알려주세요"(전화 입력 시 §23 동의 — visit_requests와 동일 문구·패턴).
3. **완료(도착 예고)**: "견적요청서를 보냈어요. **내일 이 시간까지** 3곳의 견적이 도착해요." + 준비 콘텐츠 연결("기다리는 동안: 전화 전 질문지"). UX_WRITING §1·2.
4. **결과 화면**: 견적 카드 3장 비교 — 병원명(거리·구) / **총액 볼드** / 구성(SKU: 300샷·마취크림 포함) / 조건 배지(이벤트가·첫방문가·VAT별도) / 유효기간 / ④연동 배지("또래 중앙값 62만보다 낮아요", 분포 n≥5일 때만). 하단 고지: "거리·조건순 기계 선정이며 광고 순위가 아니에요"(§27 서사).
5. **연결**: 카드에서 [이 병원으로 방문 예약] → **기존 visit_requests 플로우로 합류**(신규 개발 없음). 이 시점에만 유저 연락처가 병원 전달 경로에 실림. [전화하기]도 병기(안심번호는 후순위).

## 2. 데이터 모델 — 0013
```sql
create table quote_requests (
  id uuid pk default gen_random_uuid(),
  procedure_id text references procedures(id),      -- 견적 결과에서 진입 시 자동
  concerns text[],                                   -- CONCERNS ids
  age_band text, budget_max int,                     -- 만원
  downtime text check (downtime in ('none','weekend','week','any')),
  region_label text, lat double precision, lng double precision,
  note text,                                         -- 자유 메모(§56 필터 후 병원 전달)
  phone text,                                        -- 선택. 병원에 절대 미전달
  notify_by_sms boolean default false,
  status text default 'submitted' check (status in
    ('submitted','collecting','quoted','viewed','connected','closed','expired')),
  sla_due_at timestamptz,                            -- 접수+영업일 24h
  created_at timestamptz default now(), updated_at timestamptz default now()
);
create table quote_replies (
  id uuid pk default gen_random_uuid(),
  request_id uuid references quote_requests(id) on delete cascade,
  hospital_id uuid references hospitals(id),
  offer_id uuid,                                     -- ① hospital_offers 연결(수집 부산물)
  total_price int, price_type text check (price_type in ('fixed','from','range','consult')),
  price_max int,                                     -- range형
  sku_summary text,                                  -- "울쎄라 300샷 풀페이스, 마취크림 포함"
  conditions text[],                                 -- event_price|first_visit|vat_excluded ...
  valid_until date,
  note text,                                         -- §56 필터 통과분만 노출
  refused boolean default false, refuse_reason text, -- 병원 거절도 기록(회신율 DB)
  created_at timestamptz default now()
);
-- RLS: 공개 정책 없음(서버 전용). 유저 결과 조회는 requestId 기반 서버 액션(uuid=열람 토큰).
```
상태머신: `submitted → collecting(운영자 착수) → quoted(≥1건) → viewed(유저 열람) → connected(방문예약 생성) | closed | expired(72h 미열람)`. phone은 connected 또는 expired+7일 후 마스킹(파기 정책 — §23 고지문과 일치).

## 3. 병원 선정 로직 (§27 방어의 핵심)
자의적 추천 배제 — **기계적·재현 가능** 선정만: ① 반경 5km 내 is_aesthetic ② (미래) 해당 시술 verified offer 보유 우선 ③ 과거 회신율 상위 ④ 동률 시 거리순, **3~5곳**. 선정 로직은 코드로 고정하고 어드민에서 수동 교체 시 사유 입력 필수(감사 로그). 노출 순서도 총액 오름차순 고정.

## 4. 컨시어지 운영 SOP (베타)
- **큐**: 어드민 새 탭 "견적요청" — 대시보드 카운트, SLA 타이머(24h) 표시. 착수 시 collecting 전환.
- **콜 스크립트**(고정): "고객 의뢰로 시술 견적을 대신 문의드립니다. ○○시술 △△ 조건이면 — ①총액(VAT 포함/별도?) ②구성(샷수·마취·재생관리 포함?) ③이벤트가라면 조건·기간 ④이 가격 유효기간" — 4항목이 그대로 quote_replies 필드. 병원 거절 시 refused 기록(회신율 자산).
- **입력**: 어드민 회신 폼 = SKU 픽커(①스키마) + 4항목. 저장 시 hospital_offers(source_type='concierge')에도 자동 기록 — **③가 ①의 수집기다.**
- **원가**: 1요청 = 3~5콜 × 12~15분 ≈ 45~60분. 베타 캡 **주 10건**(운영 7.5~10h). 초과 시 대기열 고지("이번 주 마감 — 다음 주 화요일 회신").
- **미달 처리**: 3곳 못 채우면 있는 만큼 + "2곳은 가격 비공개 방침이었어요" 정직 고지(consult도 정보다).

## 5. 컴플라이언스 체크리스트 (법무 검토 안건 그대로)
1. §27 유인·알선: 건당·성사 수수료 0(수익은 별도: 정액 노출료·유저 멤버십). 병원 선정 기계적. 연락처 공개는 유저 능동 선택. → **검토 질문: '대리 가격문의+정보 전달'이 알선에 해당하는지 자문**
2. §56: quote_replies.note·병원명 옆 문구 bannedPhrases 필터(기존 트리거·checkS56 재사용)
3. §23/개인정보: phone 수집 목적("회신 통지")·파기 시점 명시, 병원 미전달 명문화
4. 표시광고: "최저가 보장" 류 문구 금지 — 우리는 '수집 시점 견적'만 표시, valid_until 병기

## 6. 지표 & 베타 성공 기준 (4주)
`quote_request_submit`(진입점별) / SLA 준수율 / 회신 3곳 달성률 / 결과 열람률 / **connect율(방문예약 전환)** / 병원 회신율(거절률).
성공: 주 10건 소진 · 열람률 80% · connect 25% · 병원 회신율 60%. 실패 신호: 신청은 차는데 열람 안 함(→문자 통지 기본화 검토), 병원 회신율 40% 미만(→"위임 문의" 스크립트 개선 or 파트너 우선 전환).

## 8. 운영 진화 사다리 (노가다 → 플랫폼)
AI 보이스 아웃바운드는 배제(병원 데스크가 AI 콜 차단 시 관계 자산 훼손 + 의료 맥락 오류 리스크). 대신:
- **L0 수동 전화**(주 10건 캡, 통화 ~15분): 전화 1통 = 견적+SKU 1행+병원 관계 데이터 3중 생산.
- **L1 AI 콜패킷**(첫 주부터): 요청 접수 시 자동 생성 — 병원 후보 3~5(거리·회신율)+전화번호 / 조건 반영 콜 스크립트 / SKU 프리필 폼. 통화하며 빈칸만 채움(~7분). 어드민 견적요청 탭에 내장.
- **L2 통화 후처리**(주 15건+): 통화 녹음(당사자 녹음 — 상대 고지 문구 스크립트에 포함)→STT→LLM이 폼 자동 입력→운영자 검수(~4분).
- **L3 텍스트 문의 병행**(카톡채널 보유 병원 — 서베이 확인): 구조화 질문을 채널/문자로 발송, 비동기 10건 동시(~2분). 기록=데이터라 추출 자동화 공짜.
- **L4 셀프서브 회신 링크**(같은 병원 3회째): "이 링크로 회신 주시면 무료 노출" → 병원 직접 입력 = 컨시어지의 종착지이자 파트너 영업 퍼널. hospital_offers(source_type='partner_submit')로 합류.
운영 원칙: 같은 병원 재접촉 시 담당자명·선호 채널·회신율을 hospitals 메모로 축적(관계 CRM의 씨앗).

## 9. PM 실험 루프 (입력·출력)
- **입력 필드 규칙**: 최소 4개(고민·지역·예산·다운타임)로 시작. **병원이 전화에서 되물은 질문 = 다음 버전 폼 필드** (되물음 로그를 어드민 회신 폼에 기록). 필드 추가는 주 1회 배포로만(실험 단위 유지).
- **출력 포맷 실험**: 결과 카드 구성(총액 우선 vs 단가 우선 vs 분포 대비 배지)을 주 단위 변형 → 열람률·connect율로 판정. 주 10건×4주면 정성 판단 충분.
- **전달 후 1문항**: "이 견적, 결정에 도움됐나요?" — 리플레이 인터뷰와 별개의 상시 리서치 채널.

## 10. 결과 화면 — 모두닥 받은견적 추가 러닝(2차 영상)
1. **요청 조건이 아카이브 카드의 타이틀**: "임플란트 / 20대, 앞니1 / 8.14 견적완료 → 받은 견적보기(14개)" — 우리 /saved 내역도 조건 요약을 타이틀로.
2. **부대비용 분리 표기**: "검진비 9,500원"을 시술가와 분리 — 우리 conditions에 별도 라인(숨기면 신뢰 붕괴 지점).
3. **총액 재계산 문법**: "임플란트 1개 기준 총 수술비 18만원, **뼈이식 포함 시 28만원**" — 옵션 포함/미포함 총액 2줄 병기. 우리 결과 카드에 채택(마취·부대 포함가 병기).
4. 견적리뷰 리워드(네이버페이 5천)는 보류 — 대가성 리뷰 §56 리스크, 우리는 reward_disclosed 원칙 유지.
