# glowmate — 오케스트레이션 런북

> 누가 무엇을 언제 실행하는가. 태스크 1개 = PR 1개 = 에이전트 1회 실행.

---

## 에이전트 구성

| 에이전트 | 역할 | 쓰기 권한 | 산출 |
|---|---|---|---|
| `task-author` | 태스크 계약 작성 | `docs/tasks/` 만 | 계약서 |
| `task-auditor` | 계약 적대적 감사 | **없음** (읽기 전용) | PASS / REVISE / REJECT |
| `dev-executor` | 계약 1건 → PR 1개 구현 | 계약의 `touches` 범위만 | 코드 + 탐지 수단 |
| `pr-reviewer` | 계약 준수 검수 | **없음** (읽기 전용) | PASS / FAIL |

**권한 비대칭이 핵심이다.** 검수 역할(`task-auditor`, `pr-reviewer`)은 쓰기 권한이 없다. 자기가 지적한 것을 자기가 고치면 검수가 아니라 자문이 된다.

---

## 실행 루프

```
        ┌─────────────────────────────────────────┐
        │                                         │
   task-author ──→ task-auditor ──REVISE/REJECT──┘
        │                │
        │              PASS
        │                ↓
        └──────→  dev-executor ──→ pr-reviewer ──FAIL──┐
                       ↑                                │
                       └────────────────────────────────┘
                                    │
                                  PASS
                                    ↓
                                  merge
```

**루프 종료 조건**

- `task-auditor` 가 같은 태스크를 **3회 REVISE** 하면 → 태스크 정의 자체를 재설계 (총괄이 개입)
- `pr-reviewer` 가 같은 PR을 **3회 FAIL** 하면 → 계약 결함 가능성. 계약을 `task-author` 로 되돌린다
- `dev-executor` 가 "계약대로 불가능"을 보고하면 → **우회 금지.** 계약 수정 후 감사 재통과

---

## 실행 순서

### 병렬 배치

> 감사 반영으로 태스크가 33 → 40건이 되었다 (D1 분할 · F2 분할 · F5·F6·W8·W9 신설 · F3·DS2 폐기).

| 배치 | 태스크 | 선행 | 동시 |
|---|---|---|---|
| **B1** | **F1** (리포·CI·DAG검증·게이트정본·ID레지스트리) | — | 1 |
| **B0** | D1a, D2, D3, D4 · ~~DS0~~✅ | **F1** (discovery CI 필요) | 4 |
| **B0b** | **D1b** (프로토콜 선머지 후) | D1a | 1 |
| **B2** | F2a, O3, **DS1** | F1 | 3 |
| **B2b** | **F2b**, F5, DS3 | F2a · ⛔G5✅ | 3 |
| **B3** | F4, C1, **DS6** | B2b + ⛔G1·G3 | 3 |
| **B4** | C2, C3, C4, C5, W1, **DS4, DS5** | B3 | 7 |
| **B4b** | **F6** (가격상태 공용 모듈) | C4, F2b | 1 |
| **B5** | C6, W2, W3, W5, W7, W9, **DS7** | B4b | 7 |
| **B6** | C7, W4, W6, W8 | B5 | 4 |
| **B7** | O1, O2 | B6 + ⛔G4 | 2 |

### 감사가 바꾼 순서 3가지

| 변경 | 이유 |
|---|---|
| **F1이 Discovery보다 먼저** | Discovery 4건의 `on_violation: block_merge` 를 집행할 CI가 없었다. 탐지 없는 금지는 금지가 아니다(원칙 3) |
| **D1a → D1b 강제 직렬 (별도 PR)** | 사전등록과 현장조사가 한 PR에 있으면 `GIT_COMMITTER_DATE`·squash merge로 시간순 검증이 붕괴한다. 프로토콜이 base 브랜치에 **먼저 머지**돼 있어야 통제가 성립 |
| **F6이 C4 뒤로** | 가격 상태 판정은 C4 산출물의 의미에 의존. W2·W3가 공유 파일을 각자 만들던 구조를 선행 태스크로 승격 |

> 같은 배치 안의 태스크는 `touches` 가 겹치지 않도록 계약 단계에서 보장되어 있다. 겹치면 그건 계약 결함이며 감사에서 걸러진다.

### 직렬이어야 하는 지점 (병렬화 금지)

| 구간 | 이유 |
|---|---|
| F1 → 나머지 전부 | F1이 정한 경계·CI가 이후 모든 `detect` 의 기반 |
| DS0 → DS3 | G5 판정 없이 컴포넌트 레이어를 못 정함 |
| DS1 → DS4·DS5 | semantic 토큰 없이 컴포넌트를 만들면 3계층이 무너짐 |
| C4·C6 → C7 | 품질 게이트는 판정 대상이 있어야 성립 |
| C7 → W4 | 공개 판정 안 된 데이터로 랜딩을 생성하면 색인이 오염됨 |
| W2·W3 → W6 | 계측할 화면이 있어야 계측 |

## 게이트 집행

| 게이트 | 판정 입력 | 통과 전 차단되는 것 |
|---|---|---|
| **G1** | D1 (가격 노출율, 축별) | Phase 2 전체 |
| **G2** | D2 (SEO 진입 가능 롱테일 ≥100) | W4 (미달 시 채널 전략 재설계) |
| **G3** | D3 (크롤링 소스 법적·기술적 실사) | C2, C3 |
| **G4** | C7 (데이터 품질 스코어) | O1, O2 및 실데이터 공개 |
| **G5** | DS0 (seed-design 실사) | DS3 이후 컴포넌트 레이어 |

**게이트 규칙**

1. 게이트 판정 기준은 **판정 전에** 고정된다. 결과를 보고 임계값을 조정하는 것은 금지이며, 이 금지는 각 Discovery 계약의 FORBID로 집행된다
2. `dev-executor` 는 계약의 `gate` 필드를 확인하고, 통과 기록이 없으면 착수하지 않는다
3. 게이트 실패는 프로젝트 실패가 아니다. **G1은 축별 차등 판정**이라 운동·바디만 통과해도 그 축으로 출시한다

## 총괄(오케스트레이터)이 직접 하는 일

에이전트에 위임하지 않는다:

- 게이트 판정 (D1·D2·D3·DS0 결과를 받아 진행/피봇 결정)
- 배치 진입 승인 (선행 배치의 PASS 확인)
- 3회 실패 루프 개입 — 계약 재설계
- 계약 간 충돌 조정 (감사가 교차 결함을 보고했을 때)
- 가설 백로그 갱신 (검증 결과가 H1~H7을 뒤집을 때)

## 호출 형식

```
# 계약 작성
task-author   ← 태스크 ID 목록 + 워크스트림 맥락 + 중점 위험

# 감사 (계약을 쓴 저자와 다른 에이전트여야 함)
task-auditor  ← 계약 파일 경로 + 교차 대조 대상 계약 + 중점 공격 지점

# 구현 (반드시 태스크 1건)
dev-executor  ← 태스크 ID 1개

# 검수 (구현한 에이전트와 달라야 함)
pr-reviewer   ← 태스크 ID 1개 + 변경 범위
```

**저자 ≠ 감사관, 구현자 ≠ 검수관.** 같은 컨텍스트가 자기 산출물을 검증하면 자기 가정을 재확인할 뿐이다.
